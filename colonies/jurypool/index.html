1. Control Flow

The user surfaces are the control plane. You ask a question via TUI, Slack DM, or the portal at jury.cells.md. Foreman is the only cell that hears you directly. Foreman frames the question, fans it out to all 9 jurors in parallel via the deliberate tool, picks 2–3 for deep follow-ups, and synthesizes a verdict back. Verdicts persist in a SQLite file inside Foreman's well; the portal reads them by hitting Foreman's per-cell API layer (the substrate primitive — same Worker/DO as the web surface, just routed to a cell-side handler instead of a static asset).

2. Deliberation Lifecycle

One question → one verdict, in five stages. Each stage either runs on Foreman (1, 2, 4, 5) or fans out across the jury (3).

1
Frame
Foreman reads the raw question. Strips noise. Decides the deliberation shape — quick poll vs. deep deliberation.
2
Dispatch
Foreman calls deliberate(question). Question fans out to all 9 jurors in parallel.
3
Jury thinks
Each juror reads its own memory, deliberates from its persona, returns a take. All 9 in parallel; medium-effort cap to avoid throttle.
4
Deep dives
Foreman picks 2–3 takes worth pursuing. Sends follow-up questions to those jurors. They respond with elaborated reasoning.
5
Verdict
Foreman synthesizes consensus, dissent, and an actionable close. Returns verdict to the user via the original surface (Slack, email, TUI).
★ Each juror writes to its own memory on every deliberation. Nightly dream cycle consolidates new signal into durable memory files — so over time, the jury learns the user.
