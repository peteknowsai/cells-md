## Headline

**Image save isn't preserving any of our changes** — bake → save → fork results in a fork with NONE of our customizations, regardless of where they live (/home, /cell at root, /etc/profile.d, /usr/lib/node_modules), and regardless of whether rinse runs.

## What I tested tonight (after `wells-stable-2026-05-10b`)

1. Migrated cells's bake to write everything outside /home (user `cell` with HOME=/cell, DNA at /cell, env shim at /etc/profile.d/cells-env.sh, sudoers entry at /etc/sudoers.d/90-cell). Layout doc: `docs/cell-filesystem.md`.

2. Bake passed all steps: created user, pushed DNA, applied pi patches in /usr/lib/node_modules/, wrote profile.d shim. Verified pre-save: everything is in place inside the running source well.

3. Saved with `validate=true` (server-side stop+rinse+save) → 6055 MB image. Forked. Checked.

   Result: **id cell → "no such user", /cell missing, /etc/profile.d/cells-env.sh missing, sudoers entry missing, pi patches missing.** Only the system-level ubuntu base remains.

4. Hypothesized ext4 commit=30 + hard-stop drops unflushed writes. Added `sudo sync && sudo sync` before save. Re-baked. Same result — nothing survived.

5. Tested `validate=false` path (manual stop+save, no rinse). After `well stop` → `well image save` → fork: same result. Even on the SOURCE well, after stop+restart (no save involved): /cell directory itself was gone, only user `cell` (PAM-fsynced via /etc/passwd) survived.

6. Probed the OLD pre-migration `cell-base` image (baked 23:07 tonight, before this work): forking from it produces a well with no /home/well/agent, no .bashrc.d. **The old image is also empty.** Cells's §2 has been failing all night because no bake has actually been preserving our writes — we just didn't catch it.

## The wells question

The save+rinse+fork pipeline appears to be discarding the running guest's writes entirely. /etc/passwd is the one thing that survives one stop cycle, presumably because PAM fsyncs synchronously. Everything else — files written via tee, mkdir, chown, sed-edits to npm-installed packages — is gone.

Either:

- **The save is using a snapshot that pre-dates our writes** (like clonefile of an underlying base layer rather than the running guest's current disk state), or
- **The stop is hard-killing the guest mid-write-flush**, with even explicit sync not landing, or
- **Something else in the pipeline is wiping** beyond what's documented for rinseGuest

We don't have visibility from this side to tell which.
