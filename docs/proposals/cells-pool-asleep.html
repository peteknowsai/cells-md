Pool — pure-asleep

Why the egg pool stops running running VMs. The capacity wall, the half-second wake, the one-line change.

⚠️ SUPERSEDED — 2026-06-17. The egg pool described here was deleted. Measurement showed a cold boot to ssh-ready (~3.5s) is noise against the ~95s mother-ritual birth, so a pool of cold eggs buys ~3% on birth latency while carrying the entire refill/eviction/seal machinery (and its bug class). Births now cold-fork a pre-provisioned cell-base image on demand; live-cell hibernation is unchanged. Kept as a historical record of the warm-pool rationale. See the joint design: the wells repo's docs/proposals/cold-boot-substrate.html.

The wall — pool VMs eating the host

V1 shipped with a "pure-hot" pool: V1_HOT_POOL_TARGET = V1_POOL_TARGET_DEPTH = 10. Every pool egg was a running VM — 4 vCPU, ~1 GB RAM, always-on. Add four live cells and we were at 14 wells × 4 vCPU = 56 vCPU on a ~18-core box. The SSH-ready gate at boot timed out on every fresh well in a burst because the host had no cycles to give. The capacity ceiling for V1 was load-bearing pool members, not load-bearing live cells.

Pure-hot was a deliberate hedge, not a feature. A long comment at cli/cells.ts:1969 spelled out the reason: the pre-Pi3 hibernate path was scary — "kills lume and clips every sibling VM." So V1 kept zero hibernated members and ate the RAM/CPU bill in exchange for never running the dangerous wake-from-hibernate path.

Three things changed that:

  • /seal landed (Pi3 / Piece-3). Sealed wells hibernate cleanly, deterministically. The bake path produces hibernate-legal eggs by construction.
  • welld 1.0.0 admission control. WELL_MAX_CONCURRENT_BOOTS paces /start, /wake, and /create — a boot burst can't oversubscribe the host. /healthz.boot_gate is observable.
  • resident_bytes on /dashboard. Per-well RSS, so we can see what hibernate actually frees.

With that substrate in place, hot was paranoia. The question was whether the wake was as expensive as the comment claimed.

The half-second wake — measured, not guessed

One sealed pool egg (egg-0974c8), three back-to-back hibernate/wake cycles:

cycle 1cycle 2cycle 3
/hibernate API call0.60 s0.58 s0.60 s
asleep resident_bytesnullnullnull
/wake API call0.49 s0.48 s0.48 s
API return → SSH-accept0.07 s0.07 s0.07 s
total wake → SSH-ready0.56 s0.55 s0.55 s

The ~2-3 s wake comment that justified pure-hot was wildly conservative. Real wake is half a second, and resident_bytes: null while asleep confirmed wells fully releases the per-VM host process on /hibernate — the VZ XPC child is gone, not just paused. Asleep is genuinely free.

Against a birth ritual that runs tens of seconds (mother executing the HTML birthing-ritual end-to-end), a half-second wake is invisible. The case for keeping any hot buffer collapsed.

The change — one constant, flipped

The whole code change:

// cli/cells.ts
- const V1_HOT_POOL_TARGET = 10;
+ const V1_HOT_POOL_TARGET = 0;

Plus a comment rewrite at the same site documenting the new model and the measurements behind it. That's it. The cold-tier code paths all existed already — they'd been dormant since V1 cut over to pure-hot.

  • Bake path (bakePoolMember): the tier decision const tier = hotCount < V1_HOT_POOL_TARGET ? 4 : 2 now always picks tier 2. New eggs are sealed, then hibernated. Verified: egg-d60afc baked at the new constant came up status=stopped, resident_bytes=null immediately.
  • Claim path (claimGenericEgg): already prefers tier-4 then falls through to "any warm." With no tier-4 in the pool, every claim returns a tier-2.
  • Consume path (cmdBirth at line 1647): wakePoolMember(eggWell, claim.tier) → /wake → SSH-ready in 0.55 s → mother runs the ritual on a now-running VM.
  • Refill path (refillPoolToDepth): Pass 1 (cold→hot promote) is a no-op when hot target is 0; Pass 2 bakes new tier-2 eggs serially.
  • Reconcile (planReconcileEvictions): the eviction rule only fires on tier === 4 && state === "warm" && status !== "running". Tier-2 stopped is exactly what wells reports for a hibernated egg — kept, never evicted.

Existing pool members were converted in-place: hibernate each of the five awake eggs, flip its tier in pool.json from 4 → 2. No destroy/rebake. Took about 4 seconds total.

Paired with wells admission control

The capacity story is two halves — wells's WELL_MAX_CONCURRENT_BOOTS (the admission gate) and cells's V1_HOT_POOL_TARGET = 0 (no pool RAM/CPU). One paces what the box can boot in a burst; the other stops the pool from consuming what the box has.

Before: 14 wells × 4 vCPU = 56 vCPU. boot_gate auto-collapsed to limit 1 under that pressure.

After: 4 live cells × 4 vCPU = 16 vCPU on 18 cores. boot_gate relaxed to limit 3 the moment the pool went asleep. Plenty of headroom for actual cells.

Refill on consume — already there

Pool eggs are replaced two ways, both already in the code:

  • Reactive — every successful birth ends with a fire-and-forget refillPoolToDepth() call (cli/cells.ts:1711). Birth returns instantly; the replacement bake runs in the background. One consume, one bake.
  • Scheduled — cells schedule-pool-refill installs a launchd plist that ticks cells pool refill every 10 minutes. Catches drift if reactive ever fails.

Steady state: pool always trending back to depth 10. A burst of N births triggers N serial bakes (each ~30 s, paced by the admission gate). With asleep eggs costing only disk, depth is now a knob about burst size, not host RAM.

Stale wording, V2 readiness, what's next

The cli/cells.ts comments around refillPoolToDepth still describe the two-pass algorithm in hot/cold terms. They're kept — they correctly document what the code does when V1_HOT_POOL_TARGET is non-zero, which is exactly what V2's variant pool will need (per-variant hot targets for latency-sensitive variants).

BOARD.md retains the historical "V1_HOT_POOL_TARGET raised from 3 → 10" entry as a changelog item; the active-state line is updated to reflect target=0.
