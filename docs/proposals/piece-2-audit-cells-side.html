In plain English

For the version that doesn't require reading the codebase

Wells's explainer said Piece 2 needed ~2-3 days of cells-side work: build a pool manager, port identity-reset, migrate state. Reasonable estimate at the time it was written.

Then we went and looked. The cells CLI doesn't actually use any of the things Piece 2 deletes. Wells has a pool feature (well pool, POST /v1/wells/pool/refill, etc.) — we don't call any of it. We have our own pool, which we built during the V1 push because we needed pool eggs to be already-cells-shaped (DNA installed, pi binary in place, hostname pre-set). Wells's generic pool couldn't do that, so we sidestepped it.

The architecture the wells doc describes as the post-Piece-2 state? We're already running it. Cells calls POST /v1/wells with fromImage: ubuntu-base, provisions over SSH, hibernates if Tier 2, records in ~/.cells/eggs.json. That's it. Wells's primitives only, no wells-pool involvement.

The wells team can pull the trigger on Piece 2's deletion immediately. Wells's pool code can be removed without breaking anything cells-side. The half-day of wells's "deletion + regression" effort still applies — we'll re-run V1.5 and V1.10 acceptance afterward to confirm nothing in our cold-fork path was secretly leaning on a wells-pool side-effect — but the dependency map is empty on our side.

The one cells-side thing this audit surfaced is unrelated to Piece 2 but related to the spirit of it: today (2026-05-13 11:34Z) cells birth bobby stalled because welld restarted at 11:06, stopped all our pool VMs, and eggs.json didn't notice. State drift across the wells/cells boundary. Adding a one-function reconciliation routine fixes that whole class of bug — and it's the kind of thing that becomes our job to do correctly once we formally own the pool.

Why the prep doc overestimated

The slice2-prep.md scope was set when we expected to migrate from wells's pool. That model:

  • Wells's pool produces generic pre-baked wells (no cell identity yet).
  • Cells calls adoptFromPool → wells hands over a generic well.
  • Cells then runs identityReset.ts to give the adopted well a cell-shaped identity (hostname, machine-id, ssh host keys).

Under that model, S2.4 (port identityReset) is unavoidable and S2.1 (schema migration) is real because ~/.wells/pool/ has the source-of-truth pool data.

What we actually built during V1 sidesteps that whole flow:

  • bakeV1Egg creates a well with CELL_NAME already in the env passthroughs.
  • well-firstboot.service (wells team owns this, per the 2026-05-09 transition) reads CELL_NAME and bakes hostname + machine-id + ssh host keys at first boot.
  • The well hibernates with identity already locked in.
  • Wake restores; identity persists; no rotation needed.

So identityReset conceptually exists for us — it's just baked at create time, not run at adopt time. The work is already done, by a different mechanism, in a different repo.

Today's incident Why state reconciliation matters 2026-05-13 11:34Z

The bobby stall this morning is exactly the bug Piece 2 fixes in spirit — and the bug the proposed reconciliation routine fixes in code.

Sequence

  1. Welld bounced at 11:06Z (~30 min into Pete's session). Bouncing welld stops the running Tier-4 VMs.
  2. eggs.json still recorded all 9 pool eggs as state: warm, tier: 4 (i.e. "running and ready"). Welld now disagreed: all 9 were status: stopped.
  3. Pete ran cells birth bobby at 11:34Z.
  4. consumeV1Egg claimed a "warm" egg from eggs.json. wakeV1Egg noticed the well was stopped, called /start. Welld returned 200 (start command accepted), but the well was now cold-booting from scratch.
  5. The cold-boot took longer than the bridge's prewarm-and-pi-handshake window. Birth fell through to cold-fork. Cold-fork failed too (some other path-of-least-resistance error after the substrate already misbehaved once). process.exit(1).
  6. The Ink animation's render zone overwrote the stderr error line. Pete saw alive, then nothing — looked like the CLI was stalled, but it had already exited.

The fix: a reconcilePool() routine. Called at the top of every cells CLI invocation that touches the pool (birth, egg list, egg refill, etc.):

  1. Fetch GET /v1/wells (welld's truth).
  2. Walk eggs.json; for each egg whose recorded state disagrees with welld's:
    • If welld says the well is gone entirely → remove from eggs.json.
    • If welld says stopped but we said tier: 4 warm → mark state: cold and demote to tier: 2, or proactively /start + recheck.
    • If welld says hibernated but we said tier: 4 → re-classify as Tier 2.
  3. Write back atomically.

This is small (~1-2 hours including a test). It also encapsulates the "what happens when welld bounces" question that wells's doc explicitly leaves to cells (Q4: "Raw state. Hints are cells's reasoning, not wells's.").
