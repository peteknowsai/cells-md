What hermes is — and what shape of harness it is

hermes-agent (Nous Research, v0.14.0) is a self-improving agent — its own skills system, cross-session memory, a learning loop, a persona file, and its own messaging gateway. It is not a coding CLI; it's a general agent in its own right.

In cells terms, hermes joins claude-code and codex as a subscription harness: a single agent CLI run on a flat-cost subscription, which birth activates rather than builds a stack around. A hermes cell gets no cells-side extensions, no pi packages, no birth-wired Slack/email — and that is not a stripped cell, because hermes already carries all of that itself. The capability stack pi gets from cells, a hermes cell gets from hermes. (The codex harness framing applies verbatim: "any integrations come through the harness's own surface.")

It differs from codex in two ways. hermes is a general agent, not a coding machine. And hermes is persistent — it has a long-lived JSON-RPC server, so host-bridge drives it the way it drives pi, not the per-turn codex exec way (§4).

"All the same capabilities as pi, claude-code, and codex" — concretely, that means a hermes cell is a first-class cell: birth, cells talk, cells tui, agent-comms (cells verify + peer RPC via session fork), checkpoint / sleep / wake, and its own web presence. It does not mean pi's .pi/extensions — that is pi's plugin system; hermes has its own.

gpt-5.5 on the ChatGPT subscription — the proxy, unchanged

The key finding

cli/proxy.ts needs zero changes — same as it needed zero changes for codex. It already has everything hermes needs.

The subscriptions proxy already routes a /codex path: a client sends Authorization: Bearer <CELLS_PROXY_SECRET>; the proxy validates it, swaps in the real ChatGPT-subscription OAuth JWT (kept fresh by the proxy's own refresh manager), injects chatgpt-account-id + originator: codex_cli, and relays to chatgpt.com/backend-api/codex/responses. The codex CLI already uses this path; pi's gpt-5.5 already uses it via the openai-codex provider.

hermes ships a codex_responses transport — the Responses-API wire protocol, the same one its own built-in openai-codex provider speaks to chatgpt.com/backend-api/codex. The egg points that transport at the proxy with a provider plugin — dna/cells/base/.hermes/plugins/model-providers/cells/ — a small ProviderProfile registering a cells provider:

# .hermes/plugins/model-providers/cells/__init__.py
register_provider(ProviderProfile(
    name="cells",
    api_mode="codex_responses",
    base_url="https://proxy.cells.md/codex",
    env_vars=("OPENAI_CODEX_API_KEY",),
    supports_health_check=False,
    # codex-CLI-shaped UA — the OpenAI SDK's default UA is bot-blocked
    # by Cloudflare on the cells.md zone before it reaches the proxy.
    default_headers={"User-Agent": "codex_cli_rs/0.0.0 (Hermes Agent)"},
))

.hermes/config.yaml then selects it with model.provider: cells and model.api_mode: codex_responses. It must be a plugin, not a config.yaml providers: entry: a config-defined provider resolves to hermes's Ollama-flavoured custom profile, which pre-flight-probes Ollama endpoints (/api/show) the codex backend 403s. A registered ProviderProfile is a first-class provider — its own api_mode, no Ollama behaviour. But the profile's api_mode alone is not enough: hermes's runtime provider resolution re-derives api_mode from the provider name and base URL and never reads the registered profile, so the explicit model.api_mode key is load-bearing (the runtime honours it only when model.provider matches). The egg's env shim (/etc/profile.d/cells-env.sh) already exports OPENAI_CODEX_API_KEY=$CELLS_PROXY_SECRET, so hermes sends Responses-API traffic with the shared secret as bearer — no ChatGPT OAuth token on the cell, exactly like codex and claude-code. The proxy forwards /codex/* verbatim and supplies the codex-specific headers (originator, chatgpt-account-id).

Resolved — the 2026-05-20 wire blocker — 2026-05-22

The "every hermes turn 403s" blocker turned out to be two independent cell-side bugs, both now fixed in the DNA; the proxy was never at fault.

1 — wrong wire protocol. The cells provider plugin registers api_mode="codex_responses", but hermes's runtime resolution (hermes_cli/runtime_provider.py) re-derives api_mode from a provider-name switch plus URL heuristics — it never consults the registered ProviderProfile. cells matched no branch, so it fell to the chat_completions default. The codex backend has no /chat/completions surface, so every turn 403'd. Fix: add model.api_mode: codex_responses to config.yaml — the runtime does honour an explicit model.api_mode when model.provider matches the runtime provider.

2 — Cloudflare bot block. With the protocol fixed, turns still 403'd with "Your request was blocked" — but at the edge of the cells.md zone, before reaching our proxy (the request was absent from the proxy log; ~180 ms vs ~530 ms for a real round trip). Isolated by curl: the OpenAI Python SDK's default User-Agent, OpenAI/Python <ver>, is flagged as a known bot by Cloudflare and blocked; any other UA passes. codex and pi cells were never affected — codex uses the Rust codex CLI, pi hits the /v1 Anthropic path; only hermes drives the OpenAI Python SDK. Fix: default_headers={"User-Agent": "codex_cli_rs/0.0.0 (Hermes Agent)"} on the cells ProviderProfile — hermes applies a profile's default_headers at client construction for any provider whose base URL matches no built-in special case.

Verified end-to-end on cell bob (2026-05-22): POST /codex/responses → 200, clean turns over both hermes chat -q and the bridge / cells talk path.

What's on the egg

One uniform generic egg, now four harnesses baked. hermes installs through Nous's own installer — curl -fsSL …/install.sh | bash -s -- --skip-setup --skip-browser — uv-based, Python 3.11, fully unattended (the setup wizard self-skips with no TTY). It is added to provisionCellInWell alongside npm install -g @openai/codex, since hermes — like codex — is not in the wells base image.

The egg also carries dna/cells/base/.hermes/: config.yaml with __MODEL__ / __THINKING__ placeholders, and the cells provider plugin under plugins/model-providers/. hermes auto-loads AGENTS.md from the working directory as its workspace entrypoint — the same file pi and codex already load. Its persona file SOUL.md it expects under $HERMES_HOME; the birth branch links the cell's SOUL.md into place. Birth activates one harness; it never installs one.

host-bridge — persistent, over the TUI gateway

This is where hermes diverges from codex. codex exec is one-shot, so host-bridge spawns a fresh process per turn. hermes runs a long-lived JSON-RPC server — the same stdio server hermes's own TUI speaks — so host-bridge drives it the way it drives pi: one SSH'd process, prompts over stdin, an event stream back. hermes is a persistent harness; the per-turn machinery codex needed does not apply.

The HarnessAdapter gains a hermesAdapter, mode: "persistent". host-bridge spawns hermes's TUI-gateway server unbuffered (python -u — buffered stdout would hang the ready handshake). The gateway greets with a gateway.ready event; translateOutbound answers it with session.create and flips the session ready once the gateway returns a session id. From there translateOutbound maps hermes's events — message.delta text, message.complete, errors — into the same pi-shaped events the talk CLI renders, and translateInbound turns a prompt into hermes's prompt.submit (and an abort into session.interrupt). forkAndAsk (the agent-comms primitive) runs hermes's -z one-shot mode — a fresh, context-free turn, the same path the other harnesses take when there's no main session to fork; hermes's own cross-session memory still gives the sibling continuity. Net: cells talk and cells tui work identically across all four harnesses, and the CLI never knows the difference — Nous even publishes a pi-RPC ↔ gateway mapping, the two protocols being close cousins.

Two small interface changes: hermes's prompt.submit carries a session id, so translateInbound gains the session handle (today it takes only the command); and CellSession gets a hermesSessionId field, the way it already has codexThreadId.

The birth ritual branch

The config blob's harness field picks the branch. hermes follows a short branch (h1–h7 in docs/birthing-ritual.html), parallel to codex's: imprint identity, substitute the model config into .hermes/config.yaml, link SOUL.md into $HERMES_HOME, write status.json, register the site service + cloud edge, checkpoint, end-test, report outcome. No birth-time session capture — the adapter opens the gateway session at connect. No extensions, no packages, no cells-side channels — short by design, like codex.
