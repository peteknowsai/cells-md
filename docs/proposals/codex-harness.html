What codex is (and isn't)

A cell's harness now has three shapes. pi is the full agent — packages, extensions, channels, a model fallback chain. claude-code and codex are coding machines: a single CLI on a subscription model, no cells-side capability stack. You talk to them, they code.

The codex harness is, in effect, the OpenAI-model harness — the counterpart to claude-code. It exists to run OpenAI's codex CLI on Pete's ChatGPT subscription, legitimately — not the metered OpenAI API. A codex cell gets no extensions, no packages, none of the cells-side Slack/email machinery; any integrations a codex cell has come through Codex's own surface (MCP servers and the like) — the harness's domain, not birth's.

How the ChatGPT subscription works — the proxy, unchanged

The key finding

cli/proxy.ts needs zero changes. It already has everything codex needs.

The subscriptions proxy already routes a /codex/* path: a client sends Authorization: Bearer <CELLS_PROXY_SECRET>; the proxy validates it, swaps in the real ChatGPT-subscription OAuth JWT (kept fresh by the proxy's own 30-minute codex refresh manager), injects chatgpt-account-id + originator: codex_cli, and relays to chatgpt.com/backend-api/codex/responses. This is the exact path pi's gpt-5.5 already uses via the openai-codex provider.

So a codex cell needs only to point the codex CLI at the proxy. The egg's .codex/config.toml declares a custom model provider:

model = "<model>"
model_reasoning_effort = "<thinking>"
model_provider = "cells"

[model_providers.cells]
base_url = "https://proxy.cells.md/codex"
wire_api = "responses"
env_key = "OPENAI_CODEX_API_KEY"

The egg's env shim (/etc/profile.d/cells-env.sh) already exports OPENAI_CODEX_API_KEY=$CELLS_PROXY_SECRET — it has, since pi's codex provider needed it. codex sends genuine Codex-CLI traffic to the proxy; the proxy makes it legitimate subscription usage. No codex login on the cell, no OAuth token on the cell — only the shared secret, same as claude-code.

What's on the egg

One uniform generic egg, all three harnesses baked on. The codex CLI is npm install -g @openai/codex (pinned) — added to provisionCellInWell, since unlike claude it isn't in the wells base image. The .codex/config.toml template carries __MODEL__ / __THINKING__ placeholders and the proxy provider block. codex auto-loads AGENTS.md as its entrypoint — the same file pi loads, now carrying __NAME__ so a codex cell knows itself. Birth activates one harness; it never installs one.

The birth ritual branch

The config blob's harness field picks the branch. codex follows a short branch (x1–x7 in docs/birthing-ritual.html), parallel to claude-code's: imprint identity, substitute the model config into .codex/config.toml, write status.json, register the site service + cloud edge, checkpoint, end-test (codex exec "say ok" answers), report outcome. No extensions, no packages, no channels.

host-bridge — per-turn, not persistent

This is the one place codex genuinely differs. pi and claude-code are persistent harnesses — host-bridge spawns one long-lived process and drives it over stdin. codex has no equivalent: codex exec is one-shot — it runs a turn to completion and exits. Multi-turn rides on codex exec resume <thread_id>.

So the HarnessAdapter interface gained a mode discriminator. The codexAdapter is mode: "per-turn": instead of buildRemoteCmd + a persistent process, it provides buildTurnCmd(sess, prompt), and CellSession.runTurn spawns a fresh ssh + codex exec per prompt. The first turn's thread.started id is captured and replayed via resume on every later turn, so the conversation persists across spawns. translateOutbound maps codex's JSONL events (thread.started, item.completed/agent_message, turn.completed, turn.failed) into the same pi-shaped events the talk CLI renders — so cells talk and cells tui work identically across all three harnesses, and the CLI never knows the difference.
