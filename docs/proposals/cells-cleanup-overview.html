Executive overview · 2026-05-12

Cells cleanup

The two teams that build Cells just agreed on a cleaner split of responsibilities. Here's what it is, why it matters, and when it lands.

1What we make

An AI agent on its own computer, in three seconds

Cells lets anyone type one command and get an AI agent running inside its own private Linux machine. The agent has files, programs, internet — a full computer of its own to do work in.

Today: cells birth → a quick animation → you're talking to an agent. From the user's perspective, it's a magic trick. Under the hood, we're keeping a few real virtual machines pre-warmed and handing one off the moment you ask.

The user experience. The middle two boxes are the part that needs to be fast.

2Who builds it

Two teams, two layers

Cells is built by two small teams that own two different layers of the stack. The clean way to think about them is property manager and moving company.

The platform team

Wells

Property manager — builds & rents apartments
  • Builds and maintains the bare Ubuntu Linux apartments (the VMs)
  • Starts them, stops them, hibernates them, wakes them
  • Manages disk images, networking, the basic plumbing
  • Provides a clean API for cells to call
  • Doesn't know or care what cells installs inside
The product team

Cells

Moving company — furnishes & moves tenants in
  • Decides what to install inside each apartment (the AI stack)
  • Pre-furnishes a few apartments and keeps them ready (the pool)
  • Picks one and changes the locks when you say cells birth
  • Talks to the agent on your behalf
  • Recovers if an agent becomes unreachable

The empty apartment is wells's. Everything in it is cells's. That's the rule.

3What we're cleaning up

The boundary between them got mixed

For convenience, wells has been doing some moving-company work — specifically, maintaining the pool of pre-furnished apartments. It was the path of least resistance when we built it. Yesterday it cost us.

Yesterday's incident · 2026-05-11 09:01 UTC

Wells was trying to enforce a rule about whether agents are reachable — "if I say a VM is running, its IP address should work." That rule is really cells's concern: only cells cares whether an agent answers; wells just runs the VMs. To enforce it, wells was poking macOS's networking about ninety-six times a minute to keep address leases fresh, and that ended up crashing in-progress address handshakes for other VMs. Four of five running agents went dark within minutes.

Wells's team mitigated in five minutes and shipped a proper fix shortly after. But the deeper question — why was wells trying to hold a cells-shaped invariant in the first place? — is what this cleanup answers.

Important to be clear on what isn't changing: wells still owns the networking layer. They're not stepping back from it — they're actually owning it more directly (see section 5: they're going to manage IP addresses themselves instead of relying on macOS to do it). What's moving to cells is the cells-shaped question — "is my agent reachable, and if not what do I do about it?" — not the underlying plumbing.

The same pattern shows up at a bigger scale with the pool of pre-furnished apartments. Wells maintains it today, but the contents are cells-shaped (which agent stack to install, which models to bake in). The cleanup moves the pool the same way: wells keeps the apartments themselves, cells decides what's in them and who gets which one.

4The cleanup, in three pieces

Smallest first, then the main piece, then a small follow-on

Piece 1

Wells removes one piece of code

30 min · wells only

Specifically the part that was poking macOS's networking too often to enforce reachability. Wells keeps everything else about networking — they just stop trying to hold a cells-shaped rule. Already disabled after the mitigation; this makes the deletion permanent.

Cells work: none.

Piece 2 — the big one

Cells takes over the pool

~3 days · cells

The pool of pre-furnished apartments moves from wells to cells. Most of the machinery is already on the cells side — this is consolidation, not building from scratch.

After this piece, wells is purely a VM platform. We're purely the AI agent product on top.

Cells work: ~2.5 days of code, one PR. Then wells deletes their copy (half a day).

Piece 3

Wells simplifies VM creation

30 min · wells

Once the pool is ours, wells can simplify how they create fresh VMs (they no longer have to make every VM hibernate-ready by default). Slightly faster fresh births as a bonus.

Cells work: one regression test, an hour.

5The bonus fix wells found

A substrate-level limit, going away

Bonus — independent of the cleanup

Static IP addresses

While planning the cleanup, wells looked deeper and found a long-standing limit: macOS's networking can only assign IP addresses to four VMs at a time. That's been the source of intermittent failures when we refill the pool quickly.

Wells is fixing this by assigning IPs themselves instead of asking macOS. About 11 hours of wells-side work; we don't have to change anything. It lands before the big piece (cells's pool) so we inherit a working platform from day one.

7What could go sideways

Three categories, all small

Already mitigated
The 4-IP networking limit

Wells's bonus fix eliminates it before we depend on it. No carry-over risk into Piece 2.

Already mitigated
The damaged VM from yesterday

Destroy and re-bake on 5/17. One-time, before the main piece starts.

Watching
Identity-rotation drift

When we port wells's identity-reset code into cells, we could miss an edge case. We'll port verbatim and test that two consecutive births produce unique identities before wells deletes their copy.

8What we need from you

Otherwise: both teams have agreed on the boundary, the timing, and the signals we'll send each other. No other decisions needed right now.

If you've heard these terms in the codebase

Slice 1 / Slice 2 / Slice 3
Engineering shorthand for Piece 1, Piece 2, Piece 3 above. "Slice" just means "a chunk of work we ship as one unit." Smallest first.
S2.1 through S2.8
The eight sub-tasks inside Piece 2 (the big cells-side piece). Things like "set up the new pool data file" (S2.1), "port the identity reset code" (S2.4), "test the matrix end-to-end" (S2.8). Internal task IDs.
W.71 / W.72
Wells-side ticket numbers. W.71 is a diagnostic feature wells shipped today to help debug pool failures. W.72 is the static-IP bonus fix described in section 5.
The pool
The small set of pre-furnished apartments (pre-warmed Ubuntu VMs with the AI stack already installed) that we keep ready so cells birth can hand one off in three seconds instead of starting from scratch.
Identity rotation / identity reset
When we hand a pre-furnished apartment to a user, we change its name, its host keys, and its machine ID so each agent feels like it has its own unique machine. The previous tenant's fingerprints get wiped.
Substrate
The bottom layer — Linux VMs running on macOS. Wells owns it. "Substrate" just means "the foundation everything else sits on."
v1 acceptance
The current cells-side milestone — proving that birth, talk, and the magical 3-second user experience work reliably on the latest architecture (host-bridge, Tier 4 eggs, etc.). What we're focused on through 5/16.
ubuntu-base / cell-base / variant egg
Three layers of disk image, from bottom to top. ubuntu-base is wells's bare Ubuntu (the empty apartment). cell-base is ours: Ubuntu plus the agent stack installed (the furnished apartment, ready to move into). Variant eggs are cell-base plus extras specific to one kind of agent.
