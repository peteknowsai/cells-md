Root cell — agent runs as root, HOME=/root

Why we retired the cell Unix user, what changed, and how it fixes the EACCES class of bugs forever.

Status — 2026-05-15 · shipped on main

Inside every cell, the agent now runs as root with HOME=/root. The previous cell Unix user (uid 1001 with NOPASSWD sudo) is retired — wells's ubuntu-base still ships it, but cells doesn't use it. DNA lives at /root (not /cell); claude/pi/codex are root-owned global npm installs that the agent (also root) can update freely. Verified end-to-end: pi cell birth + talk green; codex/claude cell birth + talk green (TODO once wells's lume wake bug is fixed — see followups).

The trigger — claude couldn't auto-update

From inside a claude-code cell, claude's self-updater diagnosed:

Root cause: claude is a root-owned global npm install, but the cell
runs as the non-root cell user — the auto-updater has nowhere it can
write.

- Running version 2.1.139, latest is 2.1.142 (3 releases behind).
- /usr/bin/claude → /usr/lib/node_modules/@anthropic-ai/claude-code/
  — all root:root, not writable by cell (uid 1001).

Same shape applies to pi and codex — all three harnesses install via sudo npm install -g at bake time, all root-owned, all unwritable by uid 1001. The auto-updater hits EACCES and self-disables. Cells fall behind quietly; nothing surfaces until you try to update from inside.

The choice — root, not user-local npm

Two paths to fix this:

A. Run the agent as rootB. Keep cell, install globals user-local
Change scopeSingle user-flip in host-bridge + DNAnpm prefix + PATH + chown across every install
Auto-updateJust works (root owns /usr/lib)Just works (cell owns /cell/.npm-global)
Apt installsNo sudo prefix neededStill needs sudo
Mental modelOne user. The VM is the sandbox.Two users with parallel install paths
npm root warningsYes (advisory; designed for shared boxes)No

A wins. The argument for the cell Unix user was security isolation, but the cell user already had NOPASSWD sudo — the isolation was theatrical. The actual isolation boundary is the VM. With root inside:

  • The EACCES class of bugs disappears entirely
  • One user, one mental model, no sudo ceremony in scripts
  • Tools that warn about running as root were designed for multi-tenant Linux servers — a single-purpose VM owned by an agent is exactly the case where the warning doesn't apply

What changed

54 files swept; behavior changes in 5 places:

  • host-bridge.ts — all three harness adapters (pi, claude-code, codex) build their remote command as exec sudo bash -lc 'export HOME=/root; cd /root && exec <harness>'. Was sudo -u cell -H bash -lc ....
  • cells.ts provisionCellInWell — DNA push lands at /root via pushLocalDirToWell; bun install + pi install + codex install all run via sudo bash -lc (no -u cell). Final chown -R root:root /root normalizes ownership (the host-side tar push leaks the Mac's uid 501 onto archive entries; root-only ownership keeps ls honest).
  • cells.ts wellExecCapture + mother's well-tools well_exec — the user="cell" branch now sudoes to root with HOME=/root set inline. The label "cell" means "the agent's effective context" rather than literally "Unix user named cell."
  • register-site-service.sh — the systemd-equivalent service that runs /root/site/server.ts wraps as sudo bash -c 'export HOME=/root; ... exec bun ...'.
  • DNA + scripts + docs — every /cell/... path was renamed to /root/.... The ritual at docs/birthing-ritual.html writes identity files under /root; pi extensions resolve $HOME/... which is now /root/....

The new filesystem layout

/root/                   ← HOME for the agent (uid 0). SSH+sudo lands here.
├── .pi/                  ← pi harness state (settings.json, extensions/, status.json)
├── .claude/              ← claude-code harness state (settings.json)
├── .codex/               ← codex harness config (config.toml)
├── .tmux.conf            ← per-cell terminal chip (filled at birth)
├── .ssh/                 ← (unused in cells; substrate has its own)
├── AGENTS.md SOUL.md IDENTITY.md CELLS.md CONTACTS.md HEARTBEAT.md MEMORY.md TOOLS.md
├── bin/                  ← /root/bin on PATH; publish-image, cells (CLI shim), cell-status.sh
├── package.json bun.lock node_modules/
├── scripts/              ← apply-pi-patches.sh, cell-color.sh, register-site-service.sh
├── site/                 ← /root/site/server.ts — the bun web server for <name>.cells.md
└── state/                ← memory/, mentality.md, etc. — extension-managed

Owned root:root end-to-end. The agent runs as root and writes anywhere it likes; the VM is the sandbox.

The wrapper pattern — sudo to root, HOME=/root

Wells's ubuntu-base SSHs in as user ubuntu (with NOPASSWD sudo). Every cells-side invocation that needs to act as the agent does:

sudo bash -lc 'export HOME=/root; cd /root && exec <cmd>'

or for non-bash spawns:

well exec --user=cell …    # cells.ts wellExecCapture's user="cell" branch
   ↓ becomes ↓
ssh ubuntu@<ip> -- sudo bash -lc 'export HOME=/root; <cmd>'

Three things this gets us:

  1. Root inside the VM — full filesystem access, no EACCES, npm globals auto-update.
  2. HOME=/root explicit — codex's CODEX_HOME, claude's ~/.claude, pi's cwd-relative .pi/ all resolve to /root/....
  3. bash -lc — sources /etc/profile.d/cells-env.sh (PATH includes /root/bin + bun; CELLS_PROXY_SECRET re-exported as the names pi/claude/codex expect).

What's vestigial now

  • Wells's cell Unix user — uid 1001 with NOPASSWD sudo, ships in ubuntu-base. Cells never invokes anything as cell anymore. The user sits in /etc/passwd doing nothing. Future ubuntu-base could drop it.
  • /cell directory — wells's ubuntu-base creates it as cell's home. Cells writes nothing there anymore. Empty except for the default shell dotfiles ubuntu put there at user-create.
  • scripts/configure-cell-proxy.sh — the legacy /home/well/agent retrofit script. Marked deprecated in its own header. No-op for /root cells.
  • Mother's well_exec user param — the "cell" value is preserved for back-compat but functionally means "sudo to root with HOME=/root." A future cleanup could drop the param entirely.
