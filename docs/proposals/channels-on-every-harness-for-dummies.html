Introduction

About This Book

Today, only pi cells respond to Slack. If you birth a cell with the claude-code or codex harness and tick the Slack channel during the picker, the channel is bound, the worker is deployed, the DM lands in Cloudflare — and then nothing. The cell sits there silent. This book explains why, what changes, and what the world looks like once it's fixed.

It also explains a small but load-bearing design choice that comes along with the fix: one cell has one mind. Whether you reach the cell via Slack, email, or by opening its TUI, you're in the same conversation by default. Branch to a side conversation in TUI and that stays local — your Slack channel doesn't see it. Quick scratch chats via cells talk stay separate from main on purpose.

Foolish Assumptions

This book assumes you already know:

  • What a cell is, and that each one has exactly one harness — pi or claude-code or codex, picked at birth.
  • That the Slack→cell bridge was fixed on 2026-05-16 (commit 65b315b) — the cells proxy now forwards egg-*.cells.md traffic to welld so the cell's Worker DO can reach the well's /agent WebSocket.
  • That host-bridge already drives cells talk for all three harnesses today, using a clean adapter pattern (cli/host-bridge.ts:162-345).
  • That the cell Worker (DO) and the Slack/Email Workers are already harness-agnostic — they speak pi's RPC vocabulary as a wire format and don't care which harness is on the other end.

Part IThe Gap, And The Mental Model

Chapter 1: What Works Today, What Doesn't

In This Chapter

  • The one spot where it's hardcoded to pi
  • Why cells talk already works for every harness

The Slack chain for a pi cell, after the 2026-05-16 fix:

Slack → Slack Worker → KV lookup → cell Worker (DO)
                                     ↓
                          wss://<wellname>.cells.md/agent
                                     ↓
                          cloudflared → cells proxy → welld
                                     ↓
                          guest VM :8080  ← dna/cells/base/site/server.ts
                                     ↓
                          spawns `pi --mode rpc`
                                     ↓
                          response flows back through the same WS

Three of those hops are already harness-agnostic by design:

  • Slack Worker and Email Worker speak the pi-RPC dialect as a wire format. They don't know what's on the other end.
  • The cell Worker DO (cli/worker/cell/cell-agent.ts) frames an inbound Slack/email event as {type:"prompt", message} and forwards it. Again — no harness awareness.
  • welld and the cells proxy are transport. They don't read the payload.

The one spot that's hardcoded to pi is inside the cell:

// dna/cells/base/site/server.ts:354
pi = spawn(["pi", "--mode", "rpc", "--session-dir", SESSION_DIR], ...);
🤓
Technical Stuff

The site server has its own pi supervisor with switch_session acking, lifecycle signaling to host.well:7879, and idle-grace shutdown. None of it is adapter-aware. claude-code and codex don't have a parallel implementation here, so a Slack message arrives at the cell, the WS frame is delivered to /agent on the site server, and there's nobody home to dispatch it.

Meanwhile, cells talk handles all three harnesses today because host-bridge (cli/host-bridge.ts) already implements the adapter pattern. The protocol translation is solved code — that's why cells talk claude-cell works.

🧵
Remember

The problem isn't "we don't know how to drive claude or codex from the cells stack." We do — it's working in host-bridge. The problem is the same logic isn't in the cell. Two implementations, only one finished.

Chapter 2: The Three Conversation Stores (Today)

Before the fix, here's what the on-disk session layout looks like for a single pi cell named bob1 — taken from a live ls on the well:

/root/.pi/agent/sessions/
├── bob1/              ← used by `cells talk` (via host-bridge)
└── root-bob1/         ← used by Slack/email (via site/server.ts main.jsonl)
    └── tui/           ← used by `cells tui`

Three parallel histories. The --session-dir path is deliberately different for each entry-point, with a code comment in cli/cells.ts:1289 explaining the intent — "keeps the TUI conversation isolated from the bridge's main.jsonl." It was a conscious choice. We're going to undo it.

Chapter 3: The Question That Cracked It Open

You asked: "if the TUI is unified with Slack, but the TUI can resume different conversations, how does that show up in Slack? Clearly I don't want every conversation showing up in Slack."

The answer that makes the rest of the design fall out:

🧵
Remember

One cell, one mind. Each cell has a single main thread. Slack always drives main. TUI defaults to main but can branch into side conversations that stay local. cells talk is its own scratch session, isolated on purpose.

That single rule answers every "what about X" question:

  • What about resuming an old conversation in TUI? Side, local — Slack doesn't see it.
  • What if I poke the cell with cells talk while a Slack conversation is in flight? Talk is scratch — main is untouched.
  • What about emails? Email is the same as Slack — drives main.
  • What's "the cell's public mind"? Main. That's what reads CONTACTS.md, that's what readers of cells-narrator see in the timeline.

Part IIThe Unified Design

Chapter 4: The Entry-Points Matrix

In This Chapter
  • The four entry-points and what each drives
  • Side-conversation behavior in TUI
  • Why cells talk stays separate
Entry-point Session driven Shows up in Slack channel?
Slack inbound main (it IS Slack)
Email inbound main yes — same shared thread

cells talk scratch (its own dir) no — isolated

Chapter 5: What "Side Conversations Stay Local" Means

On pi, sessions are files inside a --session-dir. Today's path layout has main.jsonl as the canonical thread; the same directory can hold any number of side files (you can create them in TUI with pi's session picker).

The new rule is simple: Slack writes only to main.jsonl. Other files in the dir coexist, accessible via TUI but invisible to Slack.

💡
Tip

If you want a private side conversation about something you don't want broadcast in the cell's Slack channel — open TUI, hit pi -r (or use claude/codex's session-picker equivalent), and start a fresh side. The cell remembers it; Slack never sees it.

Chapter 6: Why cells talk Stays Its Own Scratch

You called it out yourself — cells talk goes through host-bridge over RPC for a reason. It's the path you use for quick checks, smoke tests, "is bob1 awake," debugging. If every quick cells talk poked main, your Slack channel would fill with noise within a day.

So talk stays where it is, on its own session dir (e.g. /root/.pi/agent/sessions/<name>-talk/). Lightweight, isolated, exactly today's behavior — just renamed for clarity.

🧵
Remember

Three rings, not two. Main = the cell's public mind (Slack + email + TUI default). Side = TUI-only branches, never broadcast. Scratch = cells talk's quick-check sandbox.

Part IIIPer-Harness Plumbing

Each harness has its own session model. The "main thread" abstraction lands on each one slightly differently — but the user-facing rule is the same.

Chapter 7: pi

Pi's session storage is the simplest. --session-dir <dir> points at a directory; main.jsonl is the canonical conversation; other files in the dir are sidings. Every pi process that points at the same dir reads + appends to the same files. 

/root/.pi/agent/sessions/root-<name>/   ← keep today's canonical path
├── main.jsonl          ← THE main thread (Slack, email, TUI default)
├── 2026-05-14-debug.jsonl   ← a side, created in TUI
└── ...

/root/.pi/agent/sessions/talk-<name>/   ← clearly-named scratch path
└── main.jsonl          ← `cells talk`'s sandbox

Changes:

  • site/server.ts: no change — already pinned to root-<name>/main.jsonl.
  • cells tui (cmdTui): point at the same dir (root-<name>/) without the tui subdir. Default opens main.jsonl; pi -r shows everything else.
  • cells talk (host-bridge): rename to talk-<name>/ so its scratch nature is obvious.
💡
Tip

Keeping root-<name> as canonical is the simplest path: existing pi cells (bob1, pi-cell, mother, pulse) keep their entire conversation history. The only path that changes is the TUI's subdir, which is fresh state.

⚠️
Warning

Two pi processes (Slack and TUI) appending to main.jsonl at the same time: JSONL appends are line-atomic so the file stays valid, but each process's in-memory turn view diverges from the other until its next restart re-reads the file. In practice you only see this if you're typing in TUI right as a Slack message lands — rare, and self-healing on the next process restart. Acceptable trade.

Chapter 8: claude-code

claude-code stores sessions in ~/.claude/projects/<cwd-encoded>/<session-id>.jsonl. Every claude invocation either starts a new session (auto-generated id) or resumes one (--resume <id> or --continue for the latest).

The trick: capture a stable per-cell session id at birth, persist it, and have every entry-point resume it from then on.

/root/.cell/claude-main-session   ← session id, captured at birth time
/root/.cell/claude-talk-session   ← scratch session id, ditto

Three entry-points, all simple:

  • site/server.ts (Slack/email): on every startup, --resume $(cat /root/.cell/claude-main-session). No capture branch. No first-run special case.
  • cells tui: cd /root + claude --resume $(cat /root/.cell/claude-main-session). User-side pi-equivalent session-picker (claude's own resume UI) opens any other session = side.
  • cells talk: --resume $(cat /root/.cell/claude-talk-session). Scratch id captured at birth via the same warm-up.
🤓
Technical Stuff

Birth-time capture: claude's session ids are UUIDs claude picks itself — there's no flag to assert one up front. scripts/bake-egg.sh already runs the end-test on the egg; we extend it: send one "init" prompt to claude --print --output-format stream-json, sniff the session_id from the first system/init event, write it to /root/.cell/claude-main-session. Same warm-up creates the talk scratch id. After this, every entry-point's supervisor is a one-liner that always resumes — no capture-vs-fresh branching in the runtime.

Chapter 9: codex

Codex's per-turn model means every prompt spawns a fresh codex exec. The multi-turn binding is --resume <thread_id>, and the thread id rides on the first thread.started event of the very first turn. 

/root/.cell/codex-main-thread    ← thread id, captured at birth time
/root/.cell/codex-talk-thread    ← scratch thread id, ditto
  • site/server.ts: every prompt → codex exec resume $(cat /root/.cell/codex-main-thread) …. Always-resume; no capture branch.
  • cells tui: codex interactive (codex with no subcommand) — its own session model; defaults to a fresh interactive session. The "TUI sees Slack" promise is weaker here unless codex grows a "load thread X into interactive" flag. We'll document this limit; codex is the harness where TUI ↔ Slack mirror is least clean. Side branches are also less of a concept here.
  • cells talk: codex exec resume $(cat /root/.cell/codex-talk-thread) … — host-bridge already does the per-cell thread-id pattern in memory; we move it to a known on-disk cache.
🤓
Technical Stuff

Birth-time capture: like claude, codex's thread id is server-picked, not client-asserted. bake-egg.sh's warm-up runs one codex exec --json "init" for each scope (main + talk), captures thread_id from thread.started, persists. Supervisor never needs a capture branch.

⚠️
Warning

Codex interactive TUI doesn't currently take a "resume this thread" flag at startup the way claude does. Best-effort: TUI shows you the cell's last codex conversation (whatever codex's own UI surfaces). If we want a hard guarantee that TUI opens the Slack main thread, we may need a thin wrapper script. Not blocking for v1.

Part IVThe Code Changes

Chapter 10: The New File — dna/cells/base/lib/harness-adapters.ts

Today, the HarnessAdapter interface and the three implementations (pi, claude-code, codex) live entirely inside cli/host-bridge.ts (lines 135–345). We lift them out into DNA — the natural home, since this is cell logic that happens to also run on the Mac for talk: 

dna/cells/base/
├── lib/
│   └── harness-adapters.ts    ← NEW: HarnessAdapter + piAdapter + claudeAdapter + codexAdapter
└── site/
    └── server.ts              ← imports from ../lib/harness-adapters

cli/
└── host-bridge.ts             ← imports from ../dna/cells/base/lib/harness-adapters
💡
Tip

Mac-side TS importing from a DNA dir feels weird for two seconds, then it stops. The adapter is cell logic — Mac-side talk is just one of two callers. DNA is where it actually executes inside the cell, so DNA is where it should live. Side benefit: no bake-time copy step. The egg gets the adapter file as part of the normal DNA mirror.

Chapter 11: cli/host-bridge.ts — Pure Refactor

Behaviorally identical (almost). Delete the three adapter definitions, replace with import {getAdapter} from "../dna/cells/base/lib/harness-adapters". The CellSession class is unchanged. Rename pi's session-dir to talk-<name>/ so the scratch path is obvious.

  1. Move adapter code. Cut lines 135–345 of host-bridge.ts into dna/cells/base/lib/harness-adapters.ts. Export HarnessAdapter, piAdapter, claudeCodeAdapter, codexAdapter, getAdapter.
  2. Import. At the top of host-bridge.ts: import { getAdapter } from "../dna/cells/base/lib/harness-adapters";
  3. Rename pi session-dir. Line 444: sessionDir = `/root/.pi/agent/sessions/talk-${cellName}`; — scratch path. claude-code/codex talk paths use the claude-talk-session / codex-talk-thread caches captured at birth.
  4. Smoke. bun build cli/host-bridge.ts --target=bun clean. Restart the daemon: launchctl kickstart -k gui/$(id -u)/com.pete.cells-host-bridge. Smoke: cells talk bob1 "ping", cells talk claude-cell "ping", cells talk codex-cell "ping".

Chapter 12: dna/cells/base/site/server.ts — Adapter-Driven Supervisor

This is the meat of the change. The single-process pi supervisor becomes:

  1. Read harness at startup. const harness = readJson("/root/.pi/status.json").harness ?? "pi". bake-egg.sh already writes status.json with the harness baked in.
  2. Pick the adapter. const adapter = getAdapter(harness); (imported from ../lib/harness-adapters).
  3. Supervisor branches on adapter.mode. "persistent" = spawn one long-lived process (pi, claude-code). "per-turn" = each incoming WS prompt spawns a fresh process (codex). Mirrors CellSession.start() in host-bridge.
  4. Inbound translation. For each {type:"prompt",message} from the cell Worker DO, run it through adapter.translateInbound(cmd) (or runTurn for per-turn) before writing to the harness.
  5. Outbound translation. Every stdout line from the harness runs through adapter.translateOutbound(sess, line); the resulting pi-shaped events get broadcast to the WS clients (the cell Worker DO).
  6. Lifecycle signals. The existing agent_start / agent_end sniffing logic (lines 274–289) stays — every adapter outputs those events in their pi-shaped form, so the lifecycle hooks to host.well:7879 still fire.
  7. Session pinning is one-liner per harness (because birth-time capture already filled the cache files). pi: --session-dir /root/.pi/agent/sessions/root-<name>. claude-code: --resume $(cat /root/.cell/claude-main-session). codex (per-turn): codex exec resume $(cat /root/.cell/codex-main-thread). No capture branch in the supervisor — the cache file is always there.
💡
Tip

The cleanest split: keep the lifecycle / WS-server / site-publish parts of site/server.ts intact; replace ONLY the pi-supervisor section with an adapter-driven supervisor that wraps a CellSession-shaped object. Less invasive than a rewrite; one section in, one section out.

Chapter 13: cli/cells.ts — TUI Default Opens Main

cmdTui (lines 1254–1310) builds the remote tmux invocation. Today the pi branch uses ~/.pi/agent/sessions/root-<name>/tui — the /tui subdir explicitly isolates TUI from main. The fix: drop the subdir, point at ~/.pi/agent/sessions/root-<name>/, so pi --session-dir <dir> auto-loads main.jsonl by default. The user can still pi -r from inside TUI to pick a side conversation (any other file in the dir).

For claude-code TUI, change the invocation from bare claude to:

cd /root && claude --resume "$(cat /root/.cell/claude-main-session)"

For codex TUI we leave it as bare codex for v1 (no clean way to bind the main thread into an interactive session yet — Chapter 9 caveat).

Chapter 14: scripts/bake-egg.sh — Capture Main Session/Thread IDs

Birth-time warm-up is where the simplification lives. After the harness config is imprinted (lines 75–82 in bake-egg.sh today), add a per-harness capture step: 

elif [ "$HARNESS" = "claude-code" ]; then
  # ... existing settings imprint ...
  # Capture main + talk session ids
  echo "sudo mkdir -p /root/.cell"
  echo "MAIN_ID=\$(cd /root && echo init | sudo -E claude --print --output-format stream-json | head -1 | jq -r .session_id)"
  echo "echo \"\$MAIN_ID\" | sudo tee /root/.cell/claude-main-session > /dev/null"
  echo "TALK_ID=\$(cd /root && echo init | sudo -E claude --print --output-format stream-json | head -1 | jq -r .session_id)"
  echo "echo \"\$TALK_ID\" | sudo tee /root/.cell/claude-talk-session > /dev/null"

elif [ "$HARNESS" = "codex" ]; then
  # ... existing settings imprint ...
  # Capture main + talk thread ids
  echo "sudo mkdir -p /root/.cell"
  echo "MAIN_TID=\$(cd /root && sudo -E codex exec --json --skip-git-repo-check --dangerously-bypass-approvals-and-sandbox init | jq -rs '.[] | select(.type==\"thread.started\") | .thread_id' | head -1)"
  echo "echo \"\$MAIN_TID\" | sudo tee /root/.cell/codex-main-thread > /dev/null"
  echo "TALK_TID=\$(cd /root && sudo -E codex exec --json --skip-git-repo-check --dangerously-bypass-approvals-and-sandbox init | jq -rs '.[] | select(.type==\"thread.started\") | .thread_id' | head -1)"
  echo "echo \"\$TALK_TID\" | sudo tee /root/.cell/codex-talk-thread > /dev/null"
fi

Two cheap warm-up turns (~3-5s each), four cache files, done. The runtime supervisor never deals with capture — only with resume. Lower complexity in the hot path, all the asymmetry pushed into birth time where it belongs.

Chapter 14b: Verification — Manual Slack Smoke (Not eval-birth)

An earlier draft proposed adding Slack-DM-round-trip rows to eval-birth.ts. Honest reassessment: that's new eval machinery (Slack API auth, message send, message tail), not just a row. The cleaner scope for v1:

  • Keep eval-birth focused on --talk-verify (which already covers all three harnesses via host-bridge — proves the adapter works).
  • Slack delivery proven via manual smoke: birth a cell with --channels=slack, DM the channel, eyeball the reply.
  • A proper automated eval-channels.ts can come later as its own concern — don't conflate "the harness can chat" with "Slack delivery works."

  5. cells tui charlie + start a new claude session → that side conversation does NOT appear in #cells-charlie.
  6. cells talk charlie "ping" works and is its own scratch (doesn't pollute main).
  7. bun scripts/eval-birth.ts --combo=claude-slack --repeat=3 green.
  8. bun scripts/eval-birth.ts --combo=codex-slack --repeat=3 green.
  9. Pool members built post-merge include the adapter file. well exec -s <egg> -- ls /root/site/lib/ shows it.
  10. Existing pi cells (pi-cell, bob1, mother, pulse) are unchanged. They still respond on Slack and their TUI still works.

Ten Footguns To Watch For

  1. Restart the daemons after editing cli/host-bridge.ts. Stale code = silent failures.
  2. The bake-egg path: warm-ups MUST succeed (claude/codex) or the cell ships with empty cache files and the supervisor's --resume fails. Add a hard check that the cache files are non-empty before declaring BAKE-OK.
  3. Two pi processes appending to main.jsonl. Acceptable but real. If it bites, simplest mitigation: make TUI read-only until you explicitly type (start a new turn). Out of scope for v1.
  4. Claude session id capture — must persist on FIRST system/init; later events still carry the id but you want to write the cache as early as possible. Get this wrong and every claude restart spawns a fresh conversation.
  5. Codex thread_id staleness. If codex's underlying API ages out a thread, codex exec resume will error. The supervisor should fall through to a fresh turn (and update the cache) on that failure.
  6. Permission flags for claude-code (--permission-mode bypassPermissions, IS_SANDBOX=1) and codex (--dangerously-bypass-approvals-and-sandbox) — same as host-bridge today. Copy verbatim.
  7. HOME=/root everywhere. The cell migrated to root-owned in 2026-05-15; harnesses look for their config under HOME (~/.claude/, ~/.codex/, ~/.pi/).
  8. cd /root before invoking the harness. claude's session storage is cwd-keyed; cd-ing elsewhere fragments the history. Same applies to cells tui already.
  9. Status.json must have harness. bake-egg writes it; existing pre-fix cells may not. Phase C pushes a status.json refresh as part of the upgrade.
  10. The eval-birth test must actually verify Slack delivery, not just liveness. Add a real DM round-trip step, not just cells talk <name> "ping".

Part VIIPhase 2: One Harness Per Cell (Future)

In This Chapter

  • Why hibernation is already handled (wake-on-inbound is welld's job)
  • What "talk stays scratch" requires when there's only one process
  • The bonus: live mirror for free

Chapter 20: The Idea

After Phase 1 ships, every cell still runs two harness processes in active use: one inside the cell (site/server.ts, for Slack/email) and one on the Mac (host-bridge, spawned via SSH for cells talk). They both implement the same adapter contract and translate the same protocol. The bake-time copy is gone; the runtime duplication isn't.

Phase 2's collapse: cells talk becomes a WebSocket client to the cell's existing /agent endpoint, exactly the way the cell Worker DO already works. Host-bridge stops spawning harnesses entirely; it becomes a thin WS multiplexer or, more likely, vanishes — the CLI just opens a WS directly. 

BEFORE (Phase 1):
  cells talk → host-bridge → ssh ubuntu@<well-ip> → spawn pi/claude/codex
                                                      ↑ separate harness process

  Slack    → DO → wss://<well>.cells.md/agent → site/server.ts → pi/claude/codex
                                                                    ↑ separate harness process

AFTER (Phase 2):
  cells talk → ws://127.0.0.1:7878/agent?session=scratch
                                              ↓
                                          welld (wakes cell if needed)
                                              ↓
                                          site/server.ts ─── one supervisor
                                              ↓                   ↓
                                          main process         scratch process
                                              ↑
  Slack → DO → wss://<well>.cells.md/agent ────┘  (no session query = main)

Chapter 21: Hibernation — Already Handled By Wake-On-Inbound

The reason this works seamlessly with hibernation: welld wakes the cell on any inbound WebSocket connection to its /agent endpoint, regardless of caller. The wake trigger is TCP, not Worker-specific. The Slack chain already proves it; talk would inherit it.

Walk through a cold-start cells talk on a hibernated cell:

  1. You type cells talk bob1 "hi" at 3am after bob1 has been asleep for hours.
  2. The CLI opens a WS to ws://127.0.0.1:7878/agent?well=egg-19abf0 (welld's local listener).
  3. welld sees inbound WS for a hibernated well → triggers wake. ~0.5–2s for the VM to come back from RAM snapshot.
  4. welld waits for the guest's :8080 (site/server.ts) to be listening — typically another ~1–2s post-wake.
  5. welld forwards the WS upgrade through to site/server.ts. From your terminal's perspective: "Connecting…" for ~3s, then the bridge_ready frame arrives.
  6. You send the prompt. Same WS, same site server, same supervisor, same adapter → same harness response path Slack uses.
  7. You exit talk. WS closes. Welld's idle timer starts. ~60s later the cell hibernates again.
🧵
Remember

This is not a new mechanism. The DO has been doing exactly this for every Slack message, with the same ~3s cold-start cost. Talk would behave identically because welld doesn't care who's connecting.

🤓
Technical Stuff

The local shortcut: cells.ts already knows about ws://127.0.0.1:7878/agent as a Mac-local path (cli/cells.ts:4307). Talk uses that — skipping CF round-trips entirely — while still going through welld's normal accept-and-wake logic. Slack uses the public wss://<well>.cells.md/agent path because the Slack Worker lives in Cloudflare. Both arrive at the same welld dispatcher.

Chapter 22: Keeping "Talk Stays Scratch" When There's Only One Process

Phase 1's safety net was process isolation — talk's harness was a different process from Slack's harness, in different cwd, with different session paths. Collapse them and we need a different mechanism to keep talk's traffic out of main.

Cleanest fix: session routing on the WS upgrade.

ws://127.0.0.1:7878/agent              ← Slack/email/DO use this → main session
ws://127.0.0.1:7878/agent?session=scratch  ← talk uses this    → scratch session

Site/server.ts inspects the query string on upgrade. Each session-id maps to its own pinned conversation:

session= pi --session-dir claude resume id codex resume thread
main (default) root-<name>/ cat /root/.cell/claude-main-session cat /root/.cell/codex-main-thread
scratch talk-<name>/ cat /root/.cell/claude-talk-session cat /root/.cell/codex-talk-thread

For pi (persistent process), the supervisor runs ONE pi per session — so on first ?session=scratch connect, it spawns a second pi process bound to talk-<name>/. Two long-running pi processes per cell. Acceptable: pi's RAM cost is low, and the scratch process can hibernate-out if idle for a while (~5 min) — site/server.ts shuts it down and re-spawns on the next scratch WS.

For claude-code: same pattern — one persistent claude --print per session.

For codex: it's already per-turn — each prompt spawns a fresh process anyway. The session= param just picks which thread id to resume. Zero structural change.

Chapter 23: The Bonus — Live Mirror, For Free

Today (and after Phase 1): if you're in cells tui while a Slack message arrives, you don't see it stream in. You see it after the next TUI restart re-reads the JSONL file from disk.

After Phase 2's collapse: TUI could optionally attach as a WS client to the cell's /agent endpoint (same as talk and Slack). One harness process, multiple WS clients all receiving the same event stream live. Slack reply streams visibly in TUI as it happens; TUI input streams visibly into Slack as you type.

💡
Tip

Live mirror is genuinely a free outcome of the collapse — you don't need to add anything to get it. The hard part was always "two processes can't share in-memory state." Collapse to one process and the problem evaporates.

Chapter 24: Why We Defer

Phase 1 alone gives Pete what he asked for: Slack works on claude-code and codex; main thread shared between Slack and TUI's default open. The collapse is incremental upside, not table stakes.

Deferring Phase 2 has concrete benefits:

  • Smaller blast radius for the v1 ship. Phase 1 changes site/server.ts; Phase 2 changes host-bridge and adds welld query-string routing. One PR per shift, debug them separately.
  • Phase 2 needs welld cooperation. Routing ?session=scratch through cloudflared → cells proxy → welld → cell may or may not preserve the query string. We need to verify (or accept it as a Mac-local-only path).
  • The ergonomics of "is talk live-mirrored?" need a few days of use to surface. Maybe you LIKE that talk is scratch and don't want it visible in TUI either. Phase 2 surfaces that tradeoff in production.

So: ship Phase 1, live with it for a week, then revisit Phase 2 with real usage informing the design.

Where to Go From Here

Resolved by the design review (2026-05-16):

  • Adapter home: dna/cells/base/lib/harness-adapters.ts. DNA is its natural place; host-bridge imports from there.
  • Session/thread id capture: birth time, in bake-egg.sh. Runtime supervisor only ever resumes — no capture branch.
  • Pi session paths: keep root-<name> as canonical (no rename). TUI's /tui subdir is dropped. Talk renames to talk-<name>/.
  • Eval scope: keep eval-birth's --talk-verify (proves adapter works for every harness); Slack delivery proven via manual smoke. Don't conflate.
  • Live mirror: deferred to Phase 2 (Part VII). Falls out naturally from collapsing host-bridge.

Open questions still on the table:

  • Codex TUI ↔ main mirror. Accept v1's weaker guarantee (TUI shows the most-recent codex session, may or may not be main), or build a thin wrapper that forces it? Defer.
  • Phase 2's welld query-string routing. Will ?session=scratch survive the cloudflared → cells proxy → welld → guest hop? Test in isolation before committing to the design. Mac-local talk works regardless; only public-WS routing is at risk.

Follow-ups that fall out naturally:

  • Email + threading. The DO already speaks "from-email" payloads, which the harness sees as from-email from=… text=…. Today the response goes back to the original sender's email; threading is automatic. No change needed but worth eyeballing during Phase C.
  • Other channels (Discord? SMS? Telegram?). The same adapter pattern makes any new channel a Worker concern, not a per-harness concern. Bind a channel → DO frames the inbound as {type:"prompt",message} → adapter handles it.
