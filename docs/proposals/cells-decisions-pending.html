1V1.3 — how fast should the cell speak?

The cell speaks 2.3 seconds slower than the metric says it should

Question: do we accept that, change the metric, or do a day of engineering to claw the seconds back?

In plain English

When you type cells birth, here's what you experience:

  1. A purple progress animation appears: waking → warming → ready → alive. It takes about 5 seconds, on purpose, to give the cell time to spin up before you see a prompt.
  2. The animation finishes and you're at the talk prompt.
  3. The cell streams its greeting ("I'm a cell — a persistent agent living on my own Linux VM…").

The original target was that step 3 happens at or before 5 seconds — meaning the greeting starts streaming as the animation finishes. That would feel continuous: the cell appears, says hi, you're talking.

The reality I measured: step 3 happens around 7.3 seconds. That means after the animation finishes, there's a roughly 2-second silent pause where the prompt sits empty before the cell speaks.

The question is whether that 2-second pause matters to you. I don't know — you've never seen it on the new architecture. If it feels fine, we set the metric to 8 seconds and move on. If it feels janky, we spend a day eliminating the cause.

Technical detail

The cause is the host-bridge architecture we adopted to fix V1.0 (the talk-hang bug from 2026-05-11). Previously, pi ran inside the cell as a long-lived process. The bridge raced with pi's startup and dropped messages. The fix moved pi out: now the host-bridge daemon on the Mac spawns a fresh ssh+pi per talk session, into the cell over SSH.

That spawn pays a one-time cost every time a session starts:

  • ~1s SSH handshake
  • ~2s pi process boot + extension load (use-max, codex-proxy, memory, etc.)
  • ~1s switch_session + set_model + set_thinking_level handshake
  • ~2-3s first LLM round-trip to deepseek-v4-flash

That adds up to ~6-7s, plus the cell's wake/boot time. None of the pi-side work persists between births — each new cell pays the full cost.

Full writeup with 10-trial p50/p95 numbers in docs/perf/birth-to-greeting.md.

Three options

Recommended

Accept it

0 days · revise metric to 8s

If the 2-second pause feels acceptable when you actually use it, we just change the V1.3 target on the board from 5s to 8s and call V1 shipped.

Cost: nothing.

Risk: if users (or you) find the pause annoying later, we revisit and do option 2 then.

The metric is a number on a board. The user experience is what ships. If the experience is fine, the metric is academic.

If pause feels bad

Keep ssh+pi warm

~1 day · estimated 3-4s p50 after fix

Modify host-bridge so it pre-spawns the ssh+pi process when an egg enters the pool. By the time you birth, the pi is already running and just needs to switch sessions — saves ~3 seconds.

Cost: ~1 day of engineering. More RAM (every Tier 4 pool member now holds an extra ~100-200 MB for the ssh+pi process). 5 always-on Tier 4 members × ~150 MB = ~750 MB extra RAM.

Risk: more state to manage. If ssh+pi crashes on a pool member, we need recovery logic. Pi may also drift between birth and consume if pool members live longer.

Lower latency. Real engineering cost. Worth it if the pause is actually noticeable.

Punt

Defer to post-launch

0 days · revisit when usage data shows it matters

Same as option 1 in the short term, but explicitly track first-token-time in production telemetry and revisit if real users mention it.

Cost: nothing now. ~1 day later if you decide to do option 2 anyway.

Risk: you live with the 2s pause until then. Could feel sloppy at launch demos.

Same as option 1 in practice. Different vibe.

The cheapest way to decide Run cells birth in your terminal. Watch the animation. Notice whether there's a pause that feels off. If yes → option 2. If no → option 1.
My recommendation

Option 1 — accept it. The 5-second animation was explicitly designed to absorb UX latency. From the user's perspective, the animation finishing right as the cell starts speaking is the "magic moment" — but the cell speaking shortly after the animation finishes is also a fine experience. It's not 30 seconds, it's 2.

Option 2 is a real day of engineering, plus permanent RAM cost. Worth it only if option 1 fails the eye test. Run cells birth and decide on feel. If you say "yeah, the pause is fine", we close V1.3 and move on. If you say "no, that's bad", I build option 2 — it's a clear scope.

2V1.9 — what should the customization picker look like?

Right now, cells birth foo ignores the name "foo"

Question: what should appear on screen when someone types that?

In plain English

Today, all paths through cells birth end up at the fast pre-baked cell-base path. The cell gets a random name like cell-78e2a6. There's no way for the user to pick a model, a personality, or a specific name — it's the same generic cell every time.

You put V1.9 on the board last week with the spec: "cells birth <name> runs the customization picker (harness, model, personality, channel) and goes through mother slow-birth path." So the desired experience is: if the user types cells birth jeeves, they get a picker that lets them choose what kind of cell Jeeves is going to be.

I haven't built it yet because the UX is yours to design. Below I lay out three sub-questions that fully specify the picker. Once you answer those, building it is ~2-4 hours.

Technical detail

The code path in cli/cells.ts:1541 (cmdCreate) currently routes any "no flags" invocation to cmdCreateV1Fast — even if a name was passed. The fast path consumes a pool egg whose cell-name was assigned at bake time, ignoring the user's name. To implement the picker, the branch is:

if (name && isV1Default) {
  const config = await runPicker();           // new — Ink modal
  await cmdCreateLegacy(name, {...config});   // existing slow-birth path
  return;
}
if (isV1Default) {
  return cmdCreateV1Fast(name, opts);          // unchanged
}
// rest unchanged

The slow-birth path exists already (it's what cells birth foo --model=opus goes through). The picker is new — needs Ink components or a similar prompt library.

Three sub-questions I need answers to

Q2a — What triggers the picker?

Option A: cells birth <name> with no flags → picker. cells birth alone → fast generic. My read: this matches what you wrote.

Option B: any interactive cells birth → picker. Pickaxe always. Need --quick flag to skip.

Option C: cells birth → picker, defaults all-around, hit Enter through. cells birth --quick → bypass.

Q2b — What fields does the picker ask about?

The available CLI flags today: --harness, --model, --thinking, --extensions, --packages, --channels, --slack-channel. The board spec mentions: harness, model, personality, channel.

Open questions:

  • Harness: pi is the only one. Drop the field or keep as a placeholder?
  • Model: what's the list? Today's CLI lists opus/sonnet/haiku/gpt-5.5/gpt-5.5-pro/deepseek-v4-flash/deepseek-v4-pro — but Anthropic models trip your OAuth fingerprint, so they're out for now. Realistic list: gpt-5.5, gpt-5.5-pro, deepseek-v4-flash, deepseek-v4-pro.
  • Thinking: off / minimal / low / medium / high / xhigh / adaptive. Show or default to a sensible level?
  • Personality: v2 concept per BOARD ("Chief of Staff personality template"). Not built yet. Drop from v1 picker?
  • Channel: none / slack (auto-create #cells-jeeves). Slack adds CF Worker deploy time. Default to none?

Q2c — What does the picker look like on screen?

Two layouts to compare — mockups below.

Layout A — sequential prompts

$ cells birth jeeves ◯ Customizing cell jeeves Model: ❯ gpt-5.5 gpt-5.5-pro deepseek-v4-flash deepseek-v4-pro Thinking level: ❯ medium off minimal low medium high xhigh adaptive Extensions: ❯ memory mentality wiki dream (space to toggle, enter to continue) Channel: ❯ none slack (creates #cells-jeeves) Birthing jeeves… ◉ ◉ ◯ ◯ warming

One question per screen, arrow keys to pick, enter to confirm and advance. Linear flow. Familiar UX (matches npm init, yarn create, etc.).

Layout B — single-screen form

$ cells birth jeeves ──── Customize jeeves ────────────────────────────────── Model [ gpt-5.5 ▾ ] Thinking [ medium ▾ ] Extensions [x] memory [ ] mentality [ ] wiki [ ] dream Channel [ none ▾ ] ───────────────────────────────────────────────────────── [ Birth jeeves ] tab to nav · enter to submit · esc to cancel

All fields visible at once. Tab between, arrows within, enter to submit. More information-dense; feels more like a form. Slightly more complex to build (Ink doesn't have first-class form components — would need custom).

My recommendation

Layout A — sequential prompts. Builds on Ink primitives we already have (SelectInput, MultiSelect). Matches the conventions of npm init and similar tools so users don't need to learn anything new. Fast to build (~2h), low risk of UX edge cases.

For fields: drop harness (only pi exists), drop personality (v2 concept). Keep model, thinking, extensions, channel. Anthropic models filtered out of the model list until the Claude Code harness ships (per the OAuth fingerprint constraint in your memory).

For trigger: option A — cells birth <name> with no flags fires the picker. Bare cells birth stays the fast magic-moment path. Matches what you wrote on the board last week.

If you sign off on these, I'll build it in the next focused window. ~2-4 hours. We can refine the field list later — the structure is the same either way.
