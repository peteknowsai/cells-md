cells run — the jobs lane

A durable job primitive alongside cells talk. Designed 2026-06-12 with the homezero team after the delta-market wedge incident.

Plain-English summary

Today, handing a cell a big task works like a phone call: the caller asks and stays on the line until the work is done. Two things break. If the work outlasts the caller's patience (the timeout), the answer is lost. And if the worker silently wedges — as delta-market's did on 2026-06-12, hanging at zero output tokens for 23 hours — the silence is indistinguishable from "still working" and nothing anywhere notices.

cells run replaces the phone call with a work order: drop the task in the cell's mailbox, get a ticket number back immediately, hang up. On the cell, a babysitter (the watchdog) checks that the worker is actually producing output; a worker that goes quiet gets killed and retried once, then marked failed — visibly. When the work finishes, the result is written down on the cell and the status flows back to the mailbox, so cells jobs can answer "what happened?" without even waking the cell. cells talk goes back to being what it is: conversation.

The incident that forced this

  • delta-market's main session (318KB accreted since birth) wedged: every claude --print --resume <main> spawned by well-site hung at zero output tokens — ESTAB socket to the proxy, no frames, ever. One process sat 23h40m. Found only via ps on the cell.
  • Retries piled more wedged processes onto the same serialized main session. No job id, no status, no log — structurally invisible.
  • A fresh no-resume session answered in seconds, but the next long task wedged again — so this is not only a poisoned session; long streams through the proxy hang intermittently. That root cause is a separate open investigation (docs/BACKLOG.md); the watchdog below contains it meanwhile.

The design problem, as homezero put it: talk conflates the task payload, the wake, and the reply into one fragile synchronous socket — a chat primitive used as a job system. The fix is the pattern cells-world already trusts: the queue is the truth, the ring is just the wake.

Jobs are fire-and-forget by design: no reply_to, no waiter. A job that needs to tell a human something uses the cell's own tools (whatsapp_send, channels) — that's its work, not the transport's. Operators poll cells jobs.

Path of a job

  1. Submit (Mac, <1s): cells run <name> "<task>" generates a ULID job id and POSTs {kind:"job", job_id, text, timeout_seconds} to https://<name>.cells.md/inbox/append (Bearer CELLS_PROXY_SECRET, 15s abort, 3 retries). No wake, no SSH. Before posting it probes GET /debug for the DO's jobs capability — an old worker would misroute kind:"job" into the conversation path, so a missing capability aborts with "redeploy this cell's worker". Measured live: 0.16–0.18s to job id, awake or hibernated.
  2. Enqueue (DO): a kind:"job" branch in handleAppend persists the job into a new optional PersistedState.jobs map and answers 202 {job_id} immediately — the doorbell is fired without being awaited (today's agent path awaits well start inside the 202; jobs must not). The prompt does not go in that map — it gets its own job-prompt:<id> storage key, deleted on job_accepted; packed into the single snapshot value, a handful of max-size queued prompts would blow the DO's 128 KiB per-value cap and take all cross-event state down with them. Re-submitting an existing id is idempotent.
  3. Deliver (DO → supervisor, at-least-once): the job frame does not ride pendingFrames (its 10-minute expiry is tuned to talk timeouts and would silently drop jobs). Instead the DO's existing 25s alarm re-sends every job still in status:"queued" — no expiry — until the supervisor answers job_accepted, which it sends only after the job file is durably on disk. (A plain frame_ack means "process received the frame", which a crash can orphan.) On-cell dedupe is the job file itself, not the in-memory corr set — duplicates across zombie-WS reconnects are expected and harmless. One subtlety found live: a cell that hibernated seconds earlier leaves a zombie socket Cloudflare still reports OPEN — sends vanish and nothing would ever wake the cell. So whenever reliable work (queued jobs or pending talk frames) outlives an alarm tick, the DO rings the doorbell unconditionally; a wake on a running well is a ~100ms no-op, a real wake replaces the zombie with a fresh dial-in.
  4. Run (cell): well-site writes /root/state/jobs/<id>.json + .prompt, then spawns the harness in a transient systemd unit (systemd-run --collect --unit=cell-job-<id>-a<attempt>; output to .out.jsonl / .err, exit code to .exit). The unit's own cgroup is the restart-survival mechanism — a setsid child stays in well-site's cgroup and systemd's default KillMode=control-group kills it on every routine service restart (caught live during rollout). Fresh session, never --resume the main id. claude-code uses --output-format stream-json --verbose so every token grows the output file — the same spawn+parse recipe bake-egg.sh already proves at every birth. state/ is a cells refresh never-path, so job records survive both refresh pushes and rollbacks.
  5. Watch (cell): a 30s watchdog tick scans running jobs. Output grew → reset that job's stall counter. No growth for N ticks (claude-code: 10 ticks = 5 min; pi/codex: 20 ticks) → systemctl kill the unit's cgroup, retry once, then failed: stalled. An absolute leash (--timeout, default 1h, max 24h) is counted in ticks too. Ticks, not wall-clock: timestamps lie across hibernate/restore (the bridge heartbeat counts missed pings for the same reason), and a VM checkpoint freezes the interval together with the process, so the count stays honest. Liveness is the unit's state (systemctl is-active), not a MainPID — a not-yet-resolved or recycled pid must never read as "vanished" and trigger a spurious retry while the real run is streaming.
  6. Hold awake: a detached process is invisible to the busy/idle lifecycle — welld (the sole hibernation decider) would checkpoint the VM mid-job. The runner signals busy while any job runs and releases idle only when the job count hits zero and the main session is quiet. The watchdog is the guarantee that a wedged job can't hold the cell awake forever.
  7. Adopt (cell, after restarts): well-site restarts are routine (refresh, steward, cells model). At boot the runner re-scans the jobs dir: pid alive → re-watch; .exit present → finalize; pid dead with no exit file (OOM, restore edge) → retry-or-fail. Nothing is orphaned.
  8. Complete: watchdog sees the .exit file → extracts the result text from the stream output into .result.txt, updates the job file, and sends job_done {id, ok, summary} to the DO — re-sent on every tick and reconnect until job_done_ack lands, because the supervisor→DO direction has no reliable-delivery machinery today and a lost completion would otherwise be lost forever. The DO persists the terminal transition before it acks: were it to ack first and then fail the storage write, the runner would stop re-sending while the DO reloaded stale running state — a job stuck running forever despite a result on the cell. The files on the cell remain the source of truth regardless.
  9. Inspect (Mac): cells jobs <name> — awake cell: well exec reads the job files (full detail). Hibernated cell: GET https://<name>.cells.md/jobs returns the DO's status map — jobs never wake a cell to be listed, same stance as doctor.

Each cell runs jobs on its own harness, so the Max policy is untouched: claude-code cells reach Anthropic exactly as they do for conversation; pi/codex cells ride their own subscriptions. cells run mother is refused — mother serializes the birth ritual on mother.lock, and a detached job racing a birth is the known silent-deadlock.

Interactive mode + session targets (2026-06-15)

Why. On 2026-06-15 Anthropic split subscription metering: interactive Claude Code stays on the normal subscription limits, while claude -p (and the Agent SDK) draw from a separate, capped monthly Agent-SDK credit. The boundary is an explicit attribution header the CLI stamps on every request — verified on the wire: claude -p sends cc_entrypoint=sdk-cli; a genuine interactive session sends cc_entrypoint=cli. The proxy forwards it untouched, so running jobs through a real interactive Claude Code session (not --print) bills the interactive pool instead of the metered credit. We run the genuine claude binary either way, which is the ToS-permitted side of the line (the bans were about third-party token reuse, not automation) — this is purely about which pool the work counts against.

How (bin/interactive-claude-job.sh). --print is documented as non-interactive, and the CLI also treats any non-TTY stdout as non-interactive — so genuine interactivity needs a real PTY. The runner:

  • launches claude (no --print) inside a dedicated tmux -L cell-job-<id> socket — tmux answers the DA1/DA2/DSR capability queries the Ink TUI issues at startup (a raw pipe hangs), and the dedicated socket keeps the tmux server inside the job's systemd-unit cgroup, so systemctl kill <unit> reaps it (verified — no orphans);
  • registers two hooks via inline --settings: SessionStart → a ready marker (boots past the trust + bypass-permissions dialogs, which are pre-seeded: hasTrustDialogAccepted and skipDangerousModePermissionPrompt), Stop → a done marker plus the payload (deterministic completion — no spinner scraping);
  • injects the prompt via tmux bracketed-paste (robust for multi-line / special-char prompts), then recovers the answer from the session transcript JSONL (path from the Stop payload — works for forked sessions whose id is generated post-launch) and re-emits it as the same {assistant, result} stream-json frames claude -p would have produced, so extractJobResult is unchanged.

Session targets (cells run <name> "<task>" --session <target>):

targetsession flagscontext
fresh (default)--session-id <new>no main context — today's behavior
fork--resume <main> --fork-sessioninherits main read-only, writes to a throwaway fork — main untouched (verified: a fact planted in a base session is recalled by the fork; the base transcript is byte-identical before/after)
main--resume <main>continues main — deferred: main is single-owner (the persistent talk process holds it), so a detached job must not write to it; route through the persistent channel instead

Gating & rollout. Interactive jobs are opt-in per cell via CELLS_JOBS_INTERACTIVE=1 in the well-site env (default off → the --print path is unchanged, and session targets are honored only on the interactive path). Flip it on a cell, validate, then default-on once the fleet has soaked.

Trade-offs. Interactive mode forfeits --include-partial-messages (per-token streaming is --print-only); the transcript gives per-message granularity. Watchdog liveness therefore comes from pane-change snapshots appended to .err (a working TUI ticks its spinner/elapsed counter → byte growth; a truly wedged session freezes → the existing stall watchdog still fires). The Stop hook can fire a beat before the final assistant entry flushes, so the runner polls briefly for it (settle) before reconstructing. The talk path stays on --print for now — converting the live persistent talk renderer (which depends on the stream-json → pi-event translation) is a separate, higher-risk pass; see NEEDS_PETE.

Bounds and caps

  • Prompt ≤ 32KB at submit (413 otherwise) — the DO snapshot lives under a 128KiB-per-value storage cap, and prompts are dropped from the DO record once job_accepted lands.
  • ≤ 8 non-terminal jobs per cell (429) — a cell is one small VM; jobs are not a work queue for fan-out, they're "go do this and report".
  • The DO keeps the last 32 terminal job records (oldest evicted); the cell keeps all files under /root/state/jobs/.
  • Result summary stored at the DO ≤ 2KB; the full result stays on the cell.

Observability

  • cells doctor --json: the guest probe gains jobs_running / jobs_stalled (running jobs whose output hasn't grown inside the stall window) and the classifier flags them — pure logic, unit-tested like the incident tests.
  • steward: wedged-job detection is alert-only in v1 (the on-cell watchdog is the deterministic fix; if it isn't firing, that's judgment territory per the steward contract).
  • The DO's /debug output includes the jobs map for per-cell spelunking.

Rollout and version skew

  1. Supervisor + bin + lib ship to live cells via cells refresh --all (running cells; hibernated ones pick it up at next wake). Newborns get it free at claim-time bake.
  2. DO change ships per cell via scripts/deploy-cell-worker.sh — a manual sweep; no fleet redeploy command exists.
  3. Skew is safe in both directions: a new supervisor with an old DO simply never receives job frames; a new DO with an old supervisor re-sends the queued job each alarm until the supervisor is refreshed (unknown frame types are ignored today). The CLI's capability probe refuses to submit into an old DO at all.
