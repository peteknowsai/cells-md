Project mothers & brief-driven birth

Two changes to cells birth: a project can own its own mother, and you birth a cell by describing it in plain language instead of memorizing flags. Designed 2026-06-13 with Pete. Shipped 2026-06-13 — Stages 1a/1b on main, Stages 2/3 on feature/project-mothers.

Plain-English summary

Today there is exactly one mother — the operator that bakes every new cell — and you birth a cell by spelling out every knob as a flag: cells birth abstractor --harness=claude-code --model=opus --thinking=medium --seed=off.

Two things change. First, a project gets its own mother: zero-mother bakes homezero's cells, tagged to the zero project, so each project owns and can evolve how it births — without touching the shared global mother. Second, you can describe the cell you want and let the mother figure out the knobs: cells birth zero abstractor "national parcel resolver, opus, medium thinking". Flags still work and still pin any field you name; the brief fills the rest; the mother infers gaps and applies the project's defaults. The brief does double duty — it's both the config and the cell's seed purpose.

The load-bearing design choice that keeps this safe: the brief compiles down to the same deterministic config blob the ritual already runs. The judgment lives in one previewable "brief → blob" step; the proven, deterministic bake/end-test/postwork ritual is untouched. You get "just figure it out" without trading away the 99%-reliable birth.

The one idea underneath both features

A mother is a role, not a singleton — and the key that scopes the role is the project. There is one global mother by default; a project opts into its own. A "project mother" is nothing exotic: an ordinary special cell named <project>-mother, born the same deterministic Mac-side bootstrap the global mother is, running the same birth skill.

And the seam between "create a cell" (a job — produce an artifact) and "talk to that cell" (a conversation) is the durable artifact, not a shared session: the mother bakes the cell and writes it to the registry; conversation picks it up from there. In homezero the creator and the conversationalist are even different cells (the market cell writes Briefs; the advisor cells chat with buyers) — so artifact-mediation isn't just cleaner, it's the only thing that works.

Feature A — project mothers shipped

The grammar makes creating one fall out for free — "mother" inside a project means that project's mother:

cells birth zero mother        # create zero's mother (zero-mother), born Mac-side
cells birth zero abstractor    # birth abstractor, tagged project=zero

Concretely, the touchpoints (every other piece of the bake was already name-generic):

  1. Make one. cells birth <project> mother reuses cmdBirthSpecial's deterministic bootstrap (well create → DNA overlay → seal → pin → register). SpecialSpec grew a dnaName + project; resolveSpecialSpec synthesizes a <project>-mother spec from the shared dna/specials/mother/ template (well cells-<project>-mother, mother's harness + harnessChain), and __NAME__ substitution personalizes it. Registers special:true, pinned:true, project:<p>. No global mother is in the loop.
  2. Route births by project. motherFor(project) resolves the owning mother — <project>-mother if registered + alive, else global mother. The ritual, bake-egg, and postwork are unchanged; only attribution + the project tag change.
  3. The role test is a pure helper. isMotherName / projectOfMother / projectMotherName in lib/cell-name.ts are the single place the naming convention lives. The mother-only rules (the cells run jobs-refusal) key off isMotherName so a project mother gets them too. The <project>-mother namespace is reserved on the regular birth path, so every *-mother cell is a real special mother and the name alone is a reliable marker.

Honest caveat: project mothers ≠ parallel births (and the lock stays global)

Per-mother locks look like they buy cross-project parallelism, but mother's ritual reasoning runs as claude --print on Pete's one native Mac Claude Code → Max session. Two mothers running rituals at once contend on that single session — which is the real root of the historical ~175s concurrency SIGTERM, not just the lock. So the value of project mothers is isolation + ownership + a per-project brief front door, not throughput.

As built, the lock stayed global. The design floated mother-<name>.lock, but a per-mother lock would let two rituals enter the one Max session concurrently — re-opening the exact contention that caused the SIGTERM. So the single global birth-ritual lock is kept; project mothers serialize their rituals through it. Intra-project births are serial by design (the reliability guarantee); cross-project births serialize too. We do not promise parallel births and deliberately don't build for it. A true per-mother lock only becomes safe once the ritual no longer depends on a single shared Max session.

Feature B — brief-driven birth shipped

cells birth <project> <name> ["freeform brief"] [--flags]

cells birth zero abstractor "national parcel resolver, opus, medium thinking"
cells birth zero abstractor "..." --model=opus     # flags PIN / override the brief
cells birth zero parcelbot "..." --dry-run          # print the plan, spend no egg

The blob is the contract

The ritual consumes an opaque 8-field config blob. The brief-compiler's only job is to pre-fill opts, which flows through cmdCreate's existing resolution + validators to emit exactly this shape; everything downstream (bake-egg.sh, birth-postwork.sh) is untouched.

fieldroleload-bearing invariant
harnesspi / claude-code / codex / hermesselects config tree + end-test + update branch
modelthe model id stringmust be MODEL_IDS[key].modelId, NOT the friendly key
provideranthropic / openai-codex / openaimust match the model's provider + the harness↔provider rule
thinkingeffortvalid for the harness scale; adaptive is opus-only; sub-medium auto-bumps on some models
chainfallback model chainrebuilt LAST from (provider, model, thinking) via buildDefaultChain — never free-form
extensionspi extensionsoptional; pi-branch only; must be OPTIONAL_EXTENSIONS values
packagesnpm packagesoptional; pi-branch only
channelsslack / emailoptional; bound async in postwork (NOT live at birth-return)

The compiler lives Mac-side, and is deterministic

The whole validation gauntlet (harness↔provider↔thinking compatibility, MODEL_IDS lookup, buildDefaultChain, the thinking auto-bump) already runs Mac-side in cmdCreate before the blob is built. Compiling the brief there (lib/brief.ts#compileBrief) means the compiled hints flow through those validators for free, and the preview shows a blob that's already proven legal. As built the compiler is deterministic keyword extraction, not an LLM call — config hints are a trailing run of comma-separated tokens it recognizes (a model key, a thinking level — bare or "<level> thinking" / "thinking <level>" / "<level> effort" — or a harness, bare or "<harness> harness"). Everything before the trailing config run is the purpose, so a config-like word inside the purpose ("keep it low, friendly") is never silently consumed. An LLM-assisted resolver can later replace the extractor behind the same (brief, vocab) → CompiledBrief shape — that's the documented "later" layer, not this stage.

Precedence: an explicit --flag PINS a field; otherwise the brief fills it; otherwise cmdCreate's per-harness default fills it. One inference: an Anthropic model with no harness pinned implies claude-code (the Max policy), rather than the pi default that would fail validation. The leftover purpose becomes the cell's seed (its first message) unless --seed pinned one.

Grammar disambiguation

The brief must be quoted (the shell keeps it one argv element). Rule, applied after the flag parse:

  • strip a trailing positional that contains whitespace — that's the brief;
  • of what remains: 0 → cells birth (auto-name, unchanged); 1 → cells birth <name> (unchanged); 2 → cells birth <project> <name>.

So cells birth bob "be helpful" (name + brief) and cells birth zero api "fast chat cell" (project + name + brief) are both unambiguous, and cells birth <name> / cells birth keep working. cells birth <project> mother "..." is refused with a clear message (a project mother takes no brief).

Brief-driven births preview the compiled plan and confirm before spending an egg; --yes skips the confirm, --dry-run/--plan prints the plan and exits with no egg — matching the "trade speed for visibility" rule birth already lives by.

Hard findings from the surface map (what bit, and how it was handled)

  • Registry lock was a prerequisite. The registry's read-modify-write writes were lock-free and only incidentally safe because the single global mother lock serialized births. Shipped as Stage 1b: a shared withRegistryLock (atomic O_EXCL, dead-holder reclaim) around every cells.json writer.
  • ~8 sites hardcoded name === "mother". Audited: only the cells run jobs-refusal needed generalizing (a project mother serializes births too). The talk/shell/dream/sync sites are global-mother bootstrap fall-throughs a project mother (always a real cell) correctly passes through.
  • SPECIALS was a closed "mother"|"pulse" union — generalized via resolveSpecialSpec + a dnaName field. Both the synthesized cell name and well name are DNS-label validated (closing the >63-char and bad-character cases on the direct birth-special <project>-mother path).
  • "mother" is in RESERVED_NAMES. cells birth <project> mother routes to project-mother creation before the guard; bare cells birth mother stays blocked; and the whole *-mother namespace is reserved on the regular birth path so the name stays a reliable mother marker.
  • No end-test in birth-special. Project mothers are baked deterministically with no smoke test (like the global mother), so they don't hit the register-before-end-test bug — but pre-register-as-warming (Stage 1b) still guards their always-on loop's first proxy call. A broken project mother surfaces on her first ritual.

Staged plan — all shipped

  1. Stage 1a — register-before-end-test fix done (PR #1, on main). Two-phase registry (warming → alive), proxy reload-on-miss, throw-safety, fleet readers skip warming.
  2. Stage 1b — registry-lock foundation done (PR #2, on main). withRegistryLock + mutateRegistry across every cells.json writer; dead-holder reclaim; pre-register the pulse special before its loop; stale-warming cull.
  3. Stage 2 — project mothers done (feature/project-mothers). Generalized SPECIALS; motherFor(project); the name === "mother" audit; cells birth <project> mother. Per-mother lock deferred (see the caveat) — the lock stays global.
  4. Stage 3 — brief-driven birth done (feature/project-mothers). The <project> <name> "brief" grammar; the deterministic Mac-side trailing-run compiler (flag-pinned, default-filled, Anthropic→claude-code inferred); preview/confirm + --yes + --dry-run.
  5. Later — slash-command recipes in the brief (named blob-templates the compiler recognizes), and an LLM-assisted resolver behind the same compiler interface.

Deliberately not built

  • Per-project birth-DNA forks. All mothers share the one birth ritual; project specifics ride in the blob / birth template.
  • Per-mother locks. Deferred — they'd let two rituals hit the one Max session at once. The lock stays global until the ritual stops depending on a single shared session.
  • Mother hierarchies / auto-spawn-on-first-birth. A project mother is just a special cell you create explicitly.
  • True parallel births. The single Max session is the bottleneck (see the caveat).
  • NL compilation inside the ritual. The ritual stays deterministic; the brief compiles Mac-side to the same blob.

If a project never makes a mother, nothing changes — the global mother handles everything exactly as today. The pattern generalizes for free later: the same "role tagged to a project" shape would give a project its own pulse or steward if ever wanted.
