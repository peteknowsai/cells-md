The problem — one secret, no caller

Every cell — pi, claude-code, codex — reaches its LLM through proxy.cells.md. And every cell authenticates with the same bearer token: CELLS_PROXY_SECRET, one shared secret across the whole fleet. That's by design — the proxy validates the shared secret and swaps in the real subscription OAuth token before relaying upstream.

The side effect: the proxy saw every request but could not tell which cell sent it. Its access log labelled every caller unknown. As of this morning:

$ grep -c 'codex unknown' cells-proxy.log     57324
$ grep -c 'api unknown'   cells-proxy.log      5143
$ grep -c 'api <a-real-cell-name>' ...            0

Sixty-two thousand requests, zero attributed. You could not answer "which cell is burning the subscription," "is one cell stuck in a loop," "what is claudia's token usage." For a fleet meant to scale, that's a real blind spot.

The mechanism — the x-cell-name header

The proxy was built expecting an answer to "who's calling." On every request it reads an x-cell-name HTTP header, logs it as the caller, and — importantly — strips it before forwarding upstream, so it never leaks to Anthropic or OpenAI. It's a cells-private header, purely for our own attribution.

// cli/proxy.ts — checkClientAuth()
const cell = req.headers.get("x-cell-name") ?? "unknown";

The proxy side was always correct. The entire gap was upstream of it: no harness was sending the header. Not pi, not claude-code, not codex — the ?? "unknown" fallback fired 100% of the time. So the fix was never "change the proxy." It was "make each harness announce itself" — and the cell already knows its own name, it just had to put it on the wire.

All three harnesses, fixed

The key question was whether each harness had a supported way to attach a custom header — a config field — versus needing its code patched. The answer, for all three: yes, there's a config seam.

claude-code — ANTHROPIC_CUSTOM_HEADERS

The claude CLI honours an ANTHROPIC_CUSTOM_HEADERS environment variable (newline-separated Name: value pairs). It goes into the env block of .claude/settings.json:

{
  "env": {
    "ANTHROPIC_BASE_URL": "https://proxy.cells.md",
    "ANTHROPIC_CUSTOM_HEADERS": "x-cell-name: __NAME__"
  }
}

codex — http_headers

The codex CLI's config.toml supports an http_headers table on any model provider. It goes into the [model_providers.cells] block:

[model_providers.cells]
base_url = "https://proxy.cells.md/codex"
env_key  = "OPENAI_CODEX_API_KEY"
http_headers = { "x-cell-name" = "__NAME__" }

pi — registerProvider({ headers })

This was the open question — pi has no settings.json field or env var for request headers. But pi-ai's extension API does: pi.registerProvider() takes a documented headers option (docs/custom-provider.md: "Custom headers to include in requests"). The codex-proxy extension already calls registerProvider to route pi through the proxy — it just gained the header:

// dna/cells/base/.pi/extensions/codex-proxy/index.ts
pi.registerProvider("openai-codex", {
  baseUrl: "https://proxy.cells.md/codex",
  apiKey: secret,
  authHeader: true,
  headers: { "x-cell-name": cellName() },   // ← added
});

So pi gets a clean extension-based fix — an extra line in an extension that already exists, not a code patch.

Where the name comes from — and a pool-cell gotcha

claude-code and codex take the name from the egg's __NAME__ placeholder, substituted at birth — the same machinery that imprints identity everywhere else. pi's extension reads it at runtime. The obvious first try — os.hostname() — is wrong for pool-born cells: the egg keeps its generic egg-XXXXXX well name as its hostname, so os.hostname() returns the well, not the cell (verified — bob logged as egg-277845). The fix reads /cell/package.json's name field, which the birth ritual substitutes from __NAME__. Note: the heartbeat-watch extension has the same os.hostname() assumption and the same latent bug — out of scope here, but worth a follow-up if the pulse path is still live.

The fragile path we avoided

The reason the pi answer mattered so much: the only alternative, if pi-ai had no config seam, was to patch pi-ai's code — and that would have been the one genuinely fragile piece. It's worth recording what that would have meant, because it's why "check for a config seam first" was the right move.

cells already patches pi-ai. dna/cells/base/scripts/apply-pi-patches.sh runs at egg-bake and on every bun install, doing targeted sed/awk surgery on pi-ai's bundled, generated JavaScript. The patches that exist today work well — and why they work well is the whole point:

Existing patchWhat it anchors toWhy it's safe
URL swap — api.anthropic.com → proxy.cells.mdA literal stringUnambiguous. If pi-ai moves it, the patch no-ops — visible in the counter, harmless.
extractAccountId stubA named function signatureReplaces a whole function body. The signature is a stable, named anchor.
adaptive-thinking tweakA named function signatureOne-line insertion after a named function. Anchored to a name.

Every existing patch targets a stable, named anchor. A header-injection patch would have been a different animal:

  • It targets logic, not a name. It would have to find where pi-ai constructs the fetch() headers object — a code site inside request-building logic, in minified output. No function name, no unique string to pin to.
  • It's two sites, not one. The Anthropic and codex provider paths build requests separately — two independent needles.
  • It splices in runtime code. Not a constant or a stub — a line that has to run to read the cell name and set it on the headers.
  • It fails badly on upgrades. A logic-site splice that misses either silently reverts pi to unknown, or — if surrounding code shifted — lands wrong and breaks pi's LLM path. Every pi-ai bump becomes a patch-maintenance event with a real failure mode.
The lesson

"Fragile" didn't mean "impossible" — it meant: a patch anchored to generated-code internals instead of a stable name, doubled across two providers, splicing runtime code, with a failure mode that reaches pi's whole model path on a routine dependency update. For a release whose point is stability across all three harnesses, that's the opposite of what you want. Thirty minutes checking the extension API instead of reaching for the patch was the difference between a fragile fix and a clean one.

What's left

The code, DNA, and birth ritual are done — and the live fleet is already patched and verified (bob, claudia, cody, tommy2 all attribute correctly). Two things remain to make it true for new cells:

  • Pool re-bake. The warm eggs in the pool were baked before these DNA changes, so a cell born from one today would not carry the attribution config. cells pool drain + cells pool refill bakes fresh eggs with the new .claude/settings.json, .codex/config.toml, and codex-proxy extension. Needed before the stable release regardless.
  • Fresh-birth verification. Once the pool is re-baked, one birth per harness confirms the full path — DNA → ritual __NAME__ substitution → born cell → attributed in the proxy log.

Open question, lower stakes now: what is attribution for? If it's observability — billing visibility, spotting a looping cell, debugging — it's done. If something functional is meant to depend on it (per-cell rate limiting, routing, quotas), that's a separate build on top of the logging that now works.
