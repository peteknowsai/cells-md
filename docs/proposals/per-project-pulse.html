Per-project pulse

Pulse — the family scheduler — becomes a role keyed by project, the same way mother did: one global pulse plus opt-in <project>-pulse. Designed & built 2026-06-13 with Pete. Shipped 2026-06-13 on feature/per-project-pulse.

Plain-English summary

Today one pulse cell watches every cell's HEARTBEAT.md schedule and fires cells talk at the right times. After this change, a project can run its own pulse: 

cells birth zero pulse        # → zero-pulse

zero-pulse schedules homezero's cells; the global pulse keeps everyone else. They run in parallel — pulse firing a cells talk at one cell never blocks another. It's opt-in: the global pulse already covers every project for free, and each pulse is an always-on pinned cell (~1.9 GB RAM), so a project only pays for one when it wants its own isolation or cadence.

The whole design reduces to one rule: every cell is watched by exactly one pulse, and the Mac is the sole authority on which. Get that right and double-fires and dark schedules can't happen.

The one idea underneath it

A pulse is a role, not a singleton — and the key that scopes the role is the project. This is the exact shape of project mothers, and most of the machinery is reused: the SpecialSpec dnaName/project fields, resolveSpecialSpec, the shared dna/specials/pulse/ template, the <project>-<role> naming + reserved namespace.

But pulse differs from mother in two ways that drive the real design work:

  • No birth lock. Project mothers keep a global lock because every birth ritual hits Pete's one Max session — they're isolation/ownership, not parallelism. Pulse has no such bottleneck: different pulses fire at different cells, genuinely concurrent. So a project pulse is real sharding.
  • Continuous state. Mother is idle-on-demand. Pulse owns a live schedule table (a pulse-cache/<cell>.json + a cron block per cell) that must move with a cell when ownership changes — exactly once, with no window where two pulses fire it and no window where none do.

The decisive correction: the Mac is the sole seeder

The scary version of this design has two places deciding ownership that must agree byte-for-byte: the proxy's routing and the in-well bootstrapInbox, which on first run walked the registry to seed itself. An adversarial review found that bootstrapInbox was already dead code.

A pulse well has no copy of ~/.cells/cells.json and no Obsidian vault — only mother gets the registry, via a /bridge/registry/read runtime call. So bootstrapInbox has always returned {count:0, "registry missing"} on every real pulse. The live global pulse is seeded entirely by the proxy pushing heartbeats into its inbox.

That collapses the hard problem. There is no second resolver to keep in sync because the in-well pulse never computes ownership at all — it's a dumb drainer of whatever the Mac hands it. We deleted the registry dependency (it's now a hard no-op) rather than make it project-aware, which also removes a latent landmine: if a registry ever did appear in a pulse well, the old walk would seed the entire fleet into that pulse, and a project pulse would double-fire everything.

Ownership — one pure resolver

pulseOwner(project, cells) in cli/lib/pulse-owner.ts is the single source of truth: a project's own pulse if it's registered, special, and past the warming gate; else the global pulse. Pure, no IO, unit-tested. Two consumers, both on the Mac, both calling it:

  • cli/proxy.ts · bridgeInboxPulse — the partition. Every /heartbeat-changed push resolves the owner and writes into exactly that pulse's inbox. Exactly-once falls out: one owner per cell ⇒ one inbox per heartbeat.
  • cli/cells.ts — kill-eviction (forget from the cell's owning pulse, not a hardcoded pulse), retag migration, and the birth/death handoffs.

Handoff — no double-fire, no go-dark

EventWhat happens
Birth
cells birth zero pulse		 After promote, for each zero cell: seed it into zero-pulse → forget it from the global pulse → then start zero-pulse's loop. installPulseLoop only enables the service; a separate startPulseLoop runs after the handoff, so the new pulse writes no cron block until its cells are off the global one. Strict order ⇒ at worst a seconds-long gap, never an overlap.
Death
cells kill zero-pulse		 Zero's cells were evicted from the global pulse at birth, so they're actively failed back: each schedule is re-seeded into the global pulse, which rebuilds their cron on its next tick. Passive routing alone wouldn't do it — a cell whose only traffic is its schedule never posts again.
Retag
cells project <cell> <new>		 If the new project changes the owning pulse, migrate the schedule (seed-new-then-forget-old).
Crash
(OOM / wedge)		 The clean-kill path never runs. Manual handle: cells heartbeat reseed <project>. Automating this via mother's 30-min steward is in docs/BACKLOG.md.

Re-seeding sources the cell's last-seen HEARTBEAT.md from a Mac-side mirror (~/.cells/heartbeat-mirror/<cell>.md, written by the proxy on every change), falling back to the Obsidian vault. It's the freshest copy the system has, and it never requires waking a cell. 

birth ordering (the load-bearing invariant)

  promote zero-pulse → alive
        │
        ▼   for each zero cell:
  seed → zero-pulse inbox     ← new pulse not started yet (no cron blocks)
        │
        ▼
  forget ← global pulse        ← global stops firing this cell
        │
        ▼
  start zero-pulse.service      ← now (and only now) zero-pulse builds cron

Opt-in & cost

A project pulse is an always-on, pinned cell — it never hibernates, so it holds ~1.9 GB of RAM for as long as it lives. The global pulse is mandatory and covers every project; a project pulse is pure opt-in. cells birth <project> pulse prints the cost and confirms (a TTY prompt, or --yes to skip; non-interactive without --yes refuses rather than hang). The <project>-pulse namespace is reserved on the normal birth path, the same as <project>-mother.
