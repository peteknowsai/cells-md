Response to the wells team's 2026-05-12 boundary cleanup proposal (wells-cells-boundary-cleanup.html). We agree with the boundary. This is the cells-side implementation plan — the doc we'll build slice 2 against, shared with wells so the two sides line up.

TL;DR

  • We agree with all three slices and with the answers to Q1–Q5 below.
  • Image-layer boundary: wells owns the Ubuntu base image. Cells owns every layer baked on top (DNA, /cell user, pi, claude-code/codex, host-bridge agent, variant-specific packages).
  • Slice 1 (wells drops the lease publisher) — no cells work; ship whenever.
  • Slice 2 (pool moves to cells) is consolidation, not creation. We already have ~/.cells/eggs.json + cells egg refill + launchd cron. The work is merging wells's ~/.wells/pool/ concept into our existing egg pool, absorbing identityReset.ts, and formalising reachability recovery.
  • Slice 3 (wells simplifies createWell) — small cells-side regression pass, no code change.
  • W.72 (static-IP allocation) lands first — obsoletes the W.13 vmnet ceiling that's been our biggest substrate risk. Resequence: W.72 → boundary slice 1 → cells slice 2 → boundary slice 3.
  • Timing: post-v1-acceptance, 2026-05-19 → 2026-05-23. Two-day implementation, half-day test pass.

In plain English

Borrowing wells's property-manager frame

We agreed with our property manager (wells) that they should stop running the move-in process for our tenants (the AI agents). They keep the building, the apartment keys, the elevators, the basic utilities — and the bare apartment itself (the Ubuntu base install). We take over everything that turns a bare apartment into a place an AI agent can live in: installing the kitchen, hanging the pictures, setting up the wifi, picking which apartments to pre-furnish, and the move-in process itself.

The split is clean: the empty apartment is theirs; everything in it is ours. If a tenant complains the dishwasher is broken, that's us. If the elevator's stuck, that's them. Before, the line was fuzzy — they were stocking the fridge for us, and we ended up arguing about whose milk it was.

We already have most of the moving-company operation built — the pre-furnishing checklist, the move-in coordinator, the schedule of upcoming move-ins. It's lived alongside the property manager's version of the same thing for a while. Now we're going to be the only ones doing it, which means we delete the duplicate code on their side and make sure our version handles everything that theirs used to.

This is a 2–3 day project. We're going to wait until our current product milestone (v1 acceptance) is done before starting, because we want our existing tenants stable while we're moving the plumbing. Then we'll do it in a focused window the back half of next week.

What's not changing:

  • Tenants still come from the same apartments.
  • The product still works the same from a user's perspective — birth, talk, kill all behave identically.
  • Tenants who are mid-conversation when we start the work won't see anything.

What is changing internally: one pool of pre-furnished apartments instead of two overlapping ones, one move-in checklist instead of two that have been drifting apart, and clearer accountability when something goes wrong — if a tenant is unreachable, we know who's investigating without a cross-team conversation.

Why we're writing this

The wells team's proposal is the "what" — they want to delete ~1100 LoC of cells-shaped orchestration from welld and move ownership to us. This doc is the cells-side "how": which files we touch, what we have to build vs. what we already have, what order we do it in, and how we verify it before wells deletes their copy.

We're sharing it back with wells because the two sides need to land within the same window — wells can't delete poolFill.ts until we've ported pool refill, and we can't switch over until wells exposes hibernate/wake cleanly. A shared timeline keeps that from getting tangled.

Where we are today

Today: cells has its own egg pool, wells has its own pool, they overlap in the birth-flow fallthrough.

Where we want to be (post-slice-2)

Post-slice-2: one pool (cells), one bake recipe (cells), one identity rotation (cells). Wells reports honest state and stays out of cells's invariants.

Image layering — who owns what image

Pulling the boundary up one level: the same separation should apply to images themselves. Wells builds and maintains the bare apartment (the Ubuntu base); cells furnishes it (every layer above that). Two clean kinds of image, one boundary in between.

LayerOwnerContentProduced by
ubuntu-base (wells's published image) wells substrate Pure Ubuntu (noble) + well-firstboot.service + minimal substrate hooks (machine-id reset, netplan from cidata, /etc/.well-ready marker) wells build pipeline · R2-hosted · versioned tag
cell-base (cells's pre-bake) cells agent ubuntu-base + DNA (/cell filesystem) + cell user + pi + claude-code + codex + bun + host-bridge agent + /etc/profile.d/cells-env.sh cells bake cell-base · saved via wells's image store · R2-pushed by wells substrate
variant eggs (e.g. v1-generic, gpt-5.5+memory) cells agent cell-base + variant-specific (model keys, memory provisioning, extra packages) cells bake + cells egg refill · stored in ~/.cells/pool.json per S2.1

What this means in practice:

  • Cells's bake starts from ubuntu-base, not from cell-base when re-baking the agent layer. Right now we sometimes start from cell-base as shorthand; post-cleanup that's a cells-owned image we produce, not a substrate one we consume.
  • Wells doesn't know what's in cell-base or any egg image — they're opaque blobs to the image store.
  • If Ubuntu needs a security patch, that's wells's responsibility. Wells publishes a new ubuntu-base tag; cells re-bakes cell-base on top at our cadence.
  • If the agent stack needs a change (new pi version, DNA tweak), that's pure cells — wells doesn't get involved.

Our answers to wells's Q1–Q5

Q1 — Pool state location

~/.cells/pool.json. Symmetric with ~/.wells/, consolidates with our existing ~/.cells/eggs.json rather than splitting state across two files. Schema absorbs the hibernated-well fields from wells's poolRegistry (image, hibernate.bin path, last-warmed-at) onto the existing egg record.

Q2 — Identity reset

Moves to cells. The whole flow is cells-shaped — hostname, machine-id, DNA refresh, host-bridge wiring, /cell user re-keying. Keeping identityReset.ts in wells means piping cells-shaped config through wells's REST surface, which re-creates the same kind of leak the proposal is trying to close. Our cmdBake already does identity-style work over SSH (bakeCreateCellUser, bakeWriteProfileD); extending it to cover post-wake rotation is cheaper than the round-trip.

Q3 — Timing

Slice 2 lands 2026-05-19 → 2026-05-23. We're mid-flight on host-bridge + Tier 4 eggs (v1 acceptance) and want that stable before we shake the plumbing. Slice 1 you can ship whenever — no cells dep.

Q4 — /healthz honesty

Observed state, no hint. status: "running", ip: null is the right answer. Recovery decisions are ours; baking a hint into wells re-creates a soft version of the W.68 leak (wells reasoning about cells's reachability invariant).

Q5 — Intermittent pool refill bug

Yes, comfortable. Bake recipe is ours anyway. Flag back: if the root cause is vmnet's 4-concurrent DHCP ceiling (W.13 finding), we'll work around it on the cells side (serialize refill, extend DHCP wait, back off on timeout) rather than asking for wells code changes. If we hit something that does need substrate help, we'll bring it back to the channel.

Slice 2 — work breakdown

Eight work items, ~2.5 days, landed as one PR (no incremental shipping — pool semantics in flight should stay atomic).

S2.1

Unified pool schema

~0.5 day · cli/cells.ts, new cli/lib/pool.ts

Extend ~/.cells/eggs.json → ~/.cells/pool.json. Add hibernated-egg fields (hibernate_bin_path, image_digest, last_warmed_at, tier: 2|4). Migration: read old eggs.json on startup, rewrite as pool.json. Keep cooperative file lock.

S2.2

Pool refill in cells

~0.5 day · cli/cells.ts cmdEggRefill

Rewrite refill as: POST /v1/wells (fresh, with --no-cidata-mount by tier) → cmdBake → POST /v1/wells/<n>/hibernate for Tier 2; leave running for Tier 4. Drop calls to POST /v1/wells/pool/refill.

S2.3

Birth-from-pool path

~0.5 day · cli/cells.ts cmdBirth

Pick a hibernated egg from pool.json → POST /v1/wells/<n>/wake → identity rotation (S2.4) → mark egg claimed. Remove fallthrough to wells's pool. Tier 4 path unchanged (already in-cells).

S2.4

Absorb identityReset

~0.5 day · port from wells, new cli/lib/identity.ts

Port identityReset.ts (~200 LoC SSH-side: hostname, machine-id, DNA refresh) into cells. Call from S2.3 post-wake and from cmdBake at end-of-bake. Wells deletes its copy after we confirm.

S2.5

Reachability recovery

~0.5 day · cli/lib/recover.ts

Detect: talk-path timeout or well exec SSH timeout. Decide: stop+start (re-DHCP) first attempt, destroy+rebake on second failure. Wire into cells talk and host-bridge error path. This was the original W.68 motivation — formalising it here.

S2.6

Remove wells pool calls

~0.25 day · grep + delete

Strip cells's references to GET /v1/wells/pool and POST /v1/wells/pool/refill. Confirm no cmd path or test reads them. Wells deletes the endpoints after we confirm.

S2.7

Hibernate-legal bake

~0.25 day · cmdBake tail

Confirm bake leaves the image hibernate-legal (no cidata mounted at save time — we already do this via --no-cidata-mount at egg-create). Add an explicit hibernate-test step to bake's post-save validation.

S2.8

Test matrix

~0.5 day · existing harden-birth + new cases

Cover: refill from empty pool, refill under DHCP timeout (W.13 ceiling), birth-from-pool, fresh birth, identity uniqueness across two consecutive births, reachability recovery (stop+start succeeds, destroy+rebake fallback), Tier 4 stays running across refill.

Order within the PR

S2.1 → S2.4 → S2.2 → S2.3 → S2.5 → S2.6 → S2.7 → S2.8. Schema first so every other item builds against a stable shape; identity rotation second because S2.3 depends on it; recovery near the end because it touches every other code path; cleanup and test last.

Slice 1 + slice 3 — cells impact

Slice 1 — wells drops lease publisher

Wells does ~30 min, deletes ~250 LoC.

Cells impact: zero. The publisher's been disabled since the W.68 mitigation; we never relied on it. Reachability recovery (its original motivation) shows up as S2.5 in our slice 2 work — we were already absorbing it implicitly.

Action on our side: none. Watch for the PR, ack on the channel.

Slice 3 — wells simplifies createWell

Wells drops the boot-with-cidata → stop → restart-without-mount warming sequence. ~30 min, ~100 LoC simpler.

Cells impact: regression-test our fresh-birth path (the non-pool one, cells birth --no-pool). It should get ~6–8s faster. No cells code change.

Action on our side: one row in our test matrix, comparing wall-clock before/after.

Risks & coordination

Risk 1 — vmnet 4-concurrent DHCP ceiling (W.13) — obsoleted by W.72

Substrate limit; intermittent refill failures stem from this. Resolved by wells's W.72 static-IP design (posted 2026-05-12) — welld picks IPs from a managed pool and writes them via cidata netplan, bypassing bootpd entirely. With W.72 landing before our slice 2, refill serialization in S2.2 becomes a comfort belt rather than a load-bearing mitigation.

Risk 2 — image-level damage from W.68 storm (egg-19a4be)

Already on our list. Destroy + rebake before slice 2 starts so we have a clean baseline.

Risk 3 — migration-window pool gap

While slice 2 is in flight, refill will be paused. Existing eggs in ~/.cells/eggs.json + wells's ~/.wells/pool/ still serve births. Mitigation: land slice 2 as one PR — no half-state where one pool refills and the other doesn't. We pre-warm both pools the morning of 5/19 before starting.

Risk 4 — drift between cells's identityReset port and wells's original

If we port identityReset.ts incompletely (miss a field, miss an edge case), identity uniqueness could regress. Mitigation: port by reading wells's file line-by-line, not paraphrasing. Add S2.8 test for identity uniqueness across two consecutive births. Wells holds the delete on their side until we confirm green.
