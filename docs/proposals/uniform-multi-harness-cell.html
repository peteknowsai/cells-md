Uniform Multi-Harness Cell

Stop treating a cell as "a pi cell" or "a claude cell." A cell is one Linux box that already ships every harness binary. Which harness runs is a per-session choice, not the cell's brand. One advisor can hold a buyer ↔ WhatsApp conversation on pi/gpt-5.5 and a staff ↔ Slack conversation on claude/opus at the same time — same VM, same files, same memory, different hats.

Plain-English summary. Today the supervisor reads one HARNESS at boot and drives the whole cell through it. But every egg already ships the pi, claude, and codex binaries and all their config trees — so "harness" is really just the default the supervisor picks. This plan makes harness a property of each named session instead: buyer runs pi (fast, cheap, flat ChatGPT-sub cost), staff runs claude/opus on the warm interactive pool (the smart model, billed to the Max subscription, for real tuning). Durable memory stays physically shared because it's one filesystem; each session keeps its own conversation history and its own role.

Status — built on feature/uniform-multi-harness-cell (broad scope, 2026-06-16). The full per-session primitive ships, not a pi+claude special-case: any of pi/claude/codex as any session, on any cell. The simplification that makes this tractable. Named sessions do not need a second long-running harness process. main uses the cell's persistent process; named sessions already dispatch per-turn — pi via pi --print --session-id, claude via the warm tmux pool, codex via codex exec resume. So "two harnesses on one cell" is never "two daemons fighting" — it's main on the default harness plus named sessions that each pick their harness at dispatch. This sidesteps every hard ("large"-rated) part of the problem: no dual-process boot, no multi-harness main loop.

Why

Zero's HomeZero advisors are pi cells (gpt-5.5). They need two durable conversations on one cell: buyer ↔ WhatsApp (the user — fast, conversational) and staff ↔ Slack (operators tuning the advisor's skills/memory/behavior — where Pete wants the smart model). Named durable sessions already give two isolated conversations on one cell, on any harness. What's missing is letting those two sessions run different harnesses/models — specifically a genuine claude-code/opus staff session on a cell whose buyer half is pi.

The blocker was framed as "billing": the warm interactive pool that bills cc_entrypoint=cli (the Max subscription pool, not the metered Agent-SDK credit) only stands up when the cell's baked harness is claude-code (server.ts:86). A pi cell's only route to opus was the one-shot claude --print fallback → sdk-cli → metered. This reframe dissolves that: decouple the pool from the baked harness, and a claude-typed session on any cell rides the subscription pool. The billing problem isn't worked around — it's gone.

It's mostly already there

  • Binaries. scripts/bake-egg.sh:220 — "pre-merge eggs ship pi/claude/codex." All three binaries + their config trees (.pi/ .claude/ .codex/) are on every cell already.
  • Auth. cli/lib/cells-env.ts:43-46 exports the single proxy secret as ANTHROPIC_OAUTH_TOKEN, ANTHROPIC_AUTH_TOKEN, and OPENAI_CODEX_API_KEY on every cell; .claude/settings.json (base URL + x-cell-name header) ships in base DNA. So claude on a pi cell is already wired to the proxy.
  • Memory storage. /root/state/memory, mentality.md, wiki/ are one filesystem, session-agnostic. A claude staff session and a pi buyer session physically share them.
  • Adapters. harness-adapters.ts already defines all four adapters and getAdapter(name); askInSession exists for pi/claude/codex. The supervisor just picks one at boot.

So this is not a new bake or an install expansion. It's a dispatch change plus four targeted gaps.

Two hard requirements (Pete)

1. Shared filesystem = shared memory

All harnesses run in one VM at /root, so durable memory is physically shared — but only pi auto-ingests it (the pi memory extension). claude and codex won't read /root/state/memory + MEMORY.md unless told to. So "shared memory" is a convergence + ingestion fix, not storage:

  • Converge every harness on /root/state/memory as the canonical store (no claude-default or codex-default memory dir).
  • The shared instruction files (CLAUDE.md for claude, AGENTS.md for codex) carry a directive to load the canonical memory at session start, the way pi's extension does automatically.
  • Dream/consolidation (the pi extension) keeps writing there — so when staff (claude) tunes the advisor's memory, buyer (pi) reads it next turn, and vice-versa. That cross-pollination is the entire point of "same cell."

2. Per-session role / hat

The shared cell identity + memory pointer stay in the static instruction files. The per-session hat ("you are talking to a buyer over WhatsApp" vs "you are HomeZero staff over Slack who tune this cell") is a short markdown at /root/.cell/roles/<session>.md, injected per harness via that harness's system-prompt mechanism:

  • claude — --append-system-prompt on the --print path; a SessionStart hook (or session-scoped settings) for the warm pool.
  • pi — a use-max per-session delta: use-max already composes the system prompt from SOUL.md + friends at before_agent_start; it gains a per-session role-file append.
  • codex — prompt-prefix (codex has no native system-prompt seam).

In Zero's case the harness split happens to be the role split (pi=buyer, claude=staff), so the static files nearly suffice — but per-session role injection is the robust primitive and handles two same-harness sessions with different hats. (Exact flag names — --append-system-prompt, a pi --system equivalent — verified against each binary during build.)

Build phases (staged for incremental verify)

  1. Per-session config + dispatch. readSessionConfig + pure tests; named-turn dispatch selects the adapter per session. Default (no config) = cell harness, so zero behavior change until a config exists. Verify on a pi cell: a staff session with {harness: claude-code} routes to claude while buyer stays pi.
  2. Pool decoupling + chain entry. Stand the warm pool up on a pi cell for claude-typed sessions; add the chain entry; confirm staff opus bills cc_entrypoint=cli (the proxy attribution check), buyer untouched, RAM within cap.
  3. Role + memory convergence. /root/.cell/roles/<name>.md per-harness injection; claude/codex read canonical memory. Verify staff edits memory → buyer sees it; each session holds its own hat.
  4. Binary currency. Steward sweep keeps all three harnesses current; ensure-current on first activation. Verify a dormant claude binary updates before a staff session's first turn.
  5. Q1/Q2/Q3. Channel→session binding + per-session DO reply routing; --channels=slack:staff at birth; cells model --session. Verify Slack→staff↔Slack, WhatsApp→buyer↔WhatsApp, concurrent, replies to the right channel.
  6. Docs + rollout. Update this doc + named-sessions; refresh fleet; memory update.

Rollout

Mirrors the named-sessions rollout, and is safe by construction: with no per-session sidecar present, every code path falls back to the cell's default harness — so a refreshed cell behaves exactly as before until someone runs cells model --session. Order:

  1. Merge order. Land this branch and PR #22 (channel→session). They touch mostly different files; the only shared file is cli/cells.ts (this branch's cmdModel vs #22's parseCreateArgs — non-overlapping functions).
  2. Fleet refresh. cells refresh --all ships the new supervisor + adapters + libs + bootstrap; the steward does the same within 30 min. The pool decoupling means even pi/codex cells now instantiate a (lazy) pool — inert until a claude session enqueues.
  3. Worker redeploy only if PR #22 changes the DO/worker capability surface (this branch does not touch the DO).
  4. Per-advisor wiring (Zero). On a clean-born advisor: cells model <cell> --session=staff claude-code:anthropic/opus-4-8:medium (auto-adds the chain entry) and --session=buyer openai-codex/gpt-5.5:low; drop a roles/staff.md + roles/buyer.md hat; bind Slack→staff via #22's --channels=slack:staff. Verify: a staff turn bills cc_entrypoint=cli (proxy attribution), buyer stays gpt-5.5, both isolated, memory shared.
  5. Binary currency rides birth automatically (all three current on a fresh cell); the steward keeps long-lived cells current.

Risks

  • RAM — a warm claude pool on pi cells; mitigated by pay-as-you-go warming + the existing cap/TTL.
  • Role-injection flags — exact per-harness system-prompt seam (--append-system-prompt, pi equivalent) verified against each binary in phase 3; codex falls back to prompt-prefix.
  • Per-session DO reply routing — the piece deferred from named-sessions; today's single pendingChannel can't route two channels at once. In scope here (Q1).
  • Binary drift — the gap that motivated this section; closed by the sweep + lazy check.
