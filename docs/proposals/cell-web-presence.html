Cell web presence

How <name>.cells.md gets served — the push model, why it isn't a proxy, and how cells handle images.

Status — 2026-05-15 · shipped on feature/birth-rework

Every cell has a public page at <name>.cells.md, served whether the cell is awake, asleep, or hibernating. Live and verified on the fleet (bob, tommy2, cody, claudia) across all three harnesses. The decisive test: bob's well was stopped completely — :8080 inside went dark — and bob.cells.md still served HTTP 200. Images go through publish-image → Cloudflare Images; verified by turning cody's 1.8 MB cat PNG into a delivery URL.

The problem — a domain with nothing behind it

Each cell was always meant to have a public face at <name>.cells.md — somewhere the agent could publish things to the open web. But nothing served it. The per-cell Cloudflare Worker existed only as a Slack/email bridge; a request to <name>.cells.md just returned 401 unauthorized. The cell's own site server ran on :8080 inside the well, reachable by nobody.

The obvious fix — point <name>.cells.md at the cell's :8080 through a tunnel — has a fatal flaw: cells are built to sleep. An idle cell hibernates. A proxy-back design means the public page goes dark every time that happens — which, for an idle cell, is most of the time. You'd have to wake a cell just to look at its website.

Push, not proxy — the decision

The push model decouples site availability from cell liveness. The cell publishes while it's awake; something always-on serves. That something is the per-cell Worker's Durable Object — Cloudflare infrastructure, independent of the well.

The mechanism — site server → Worker → Durable Object

Three pieces, all cells-side:

  • Site server (dna/cells/base/site/server.ts, runs in the well). On boot and — debounced — on any change under site/public/, it builds a snapshot and POSTs it to the Worker. The agent just writes files; a filesystem watch does the rest.
  • Worker (cli/worker/cell/index.ts). Split into a Bearer-gated control plane (/inbox/append, /site/publish, /image/upload, /debug) and a public route — any other GET is <name>.cells.md, served with no auth from the stored snapshot.
  • Durable Object (cli/worker/cell/cell-agent.ts). handleSitePublish stores the snapshot (one key per file, strongly consistent — a publish is instantly live); serveSite serves it. Already per-cell, so no new infrastructure.
agent writes site/public/index.html
  → site server's fs.watch fires → debounce → POST /site/publish
    → Worker → DO.handleSitePublish (snapshot stored)
GET https://<name>.cells.md/
  → Worker public route → DO.serveSite → 200, even if the cell is asleep

Images — publish-image and Cloudflare Images

The DO snapshot caps each file at ~96 KB (Durable Object storage limit). That's fine for HTML/CSS/JS — not for a generated image. cody proved the gap on day one: its agent wrote a 1.8 MB cat PNG into site/public/, and the snapshot skipped it.

So cells don't put image files in site/public/ at all. They run publish-image <file> — baked into every cell's PATH at /root/bin/publish-image, works identically across pi, claude-code, and codex (it's a shell script). It relays the image through the Worker's /image/upload route to Cloudflare Images and prints a delivery URL the agent references in its HTML.

$ publish-image diagram.png
https://imagedelivery.net/<hash>/<id>/public
Why the upload goes through the Worker

The same posture as the proxy secret: a cell never holds a real Cloudflare credential. The CLOUDFLARE_API_TOKEN (Images-scoped) lives as a Worker secret, pushed by deploy-cell-worker.sh; the cell authenticates to its own Worker with the shared CELLS_PROXY_SECRET it already has. The Worker relays to the CF Images API and hands back the URL.

What reaches a cell, and when

Two delivery paths, and they update on different cadences:

  • The Worker is deployed per-cell at birth — deploy-cell-worker.sh always renders and deploys current Worker code. New cells get the latest Worker automatically; the live fleet was redeployed in place.
  • The DNA — site/server.ts, bin/publish-image, and the web-presence sections in CELLS.md / TOOLS.md — is baked into the egg pool. New cells inherit it only after a pool re-bake; the live fleet was patched in place.

The DNA also tells every cell about all this: CELLS.md carries web presence as a property of being a cell, and TOOLS.md carries the mechanics — write to site/public/, it auto-publishes; use publish-image for images. Both files are reached by AGENTS.md and CLAUDE.md, so all three harnesses see them. (cody, notably, figured out it had a web presence and built itself a styled page with zero prompting — the DNA now makes that explicit rather than lucky.)
