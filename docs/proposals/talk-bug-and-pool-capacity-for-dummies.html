Introduction

About This Explainer

The birth rework shipped — three harnesses, a generic pool, push-model web presence, the lot. The wrap-up listed two things still "to do": fix the claude-code talk bug, and resolve a pool capacity tension. This explainer is what each of those two things actually is, written plain-language first with the deep detail clearly marked.

The short version, so you're not in suspense: one of the two was a ghost. The claude-code talk bug had already been fixed; it only looked open because of where people were reading. The capacity wall, on the other hand, is real, and it needs one small decision.

🧵
Remember

This is an explainer, not a proposal asking for approval. Loose end #1 needs no decision at all. Loose end #2 needs one small one. Nothing here is a big ask.

Foolish Assumptions

This book assumes that you:

  • Know a cell is an agent that lives on its own little Linux VM — and that the VM is called a well.
  • Know cells are born from a pool of warm, pre-baked "eggs" so a birth is instant instead of a cold provision.
  • Know host-bridge is the daemon on Pete's Mac that drives a cell's harness over SSH when you run cells talk.
  • Would rather hear "that thing you were worried about is actually fine" than carry a phantom bug on the board forever.

Part IThe Talk Bug (The One That's Already Dead)

Chapter 1: What You Heard vs. What's True

In This Chapter
  • The claim: claude-code talk is the headline open gap
  • The test: two cells, one prompt each
  • The verdict: it works

The birth-rework wrap-up called the claude-code talk bug "the headline open gap" — the top thing left to fix. So someone went and ran it. 

$ cells talk claudia "Reply with exactly: pong"
claudia> pong

$ cells birth vctalk --harness=claude-code ...   # a brand-new cell
$ cells talk vctalk "Reply with exactly: fresh-ok"
vctalk> fresh-ok

claudia is a claude-code cell that's been alive for hours. vctalk was a claude-code cell born minutes earlier from the freshly re-baked pool. Both answered cleanly, both exited 0. claude-code cells talk. There is no open talk bug.

🧵
Remember

STATUS.md and BOARD.md already say claude-code talk is verified working. They are correct. The document that's wrong is a commit message — and a commit message, unlike a status file, can never be edited after the fact. It just sits there being wrong forever.

Chapter 2: The Chain of Bugs (And What Killed Each)

In This Chapter
  • The path a claude-code prompt actually travels
  • Three host-bridge bugs that lived on that path
  • Why "no output" was lying to everyone

There was a real bug — three of them, actually, in a row. They're worth understanding, because the way the last one looked is the whole reason this loose end got mistaken for unsolved.

When you run cells talk against a claude-code cell, the prompt travels: talk CLI → host-bridge (on the Mac) → SSH into the cell → the claude CLI in stream-json mode → the proxy → Claude Max → and all the way back. host-bridge's claudeCodeAdapter is the translator in the middle: it turns claude's event stream into the vocabulary the talk CLI speaks. Three bugs lived in that translator.

The bugWhat it wasWhat killed it
The double bash -lc wrap CellSession.start wrapped the remote command in bash -lc — but SSH re-joins its arguments with spaces and the remote shell re-parses them, so the command collapsed into a no-op and claude never even launched. host-bridge stopped double-wrapping; each adapter now owns its own bash -lc and SSH passes it through untouched.
The handshake deadlock startHandshake sat waiting for a "system/init" ready signal — but claude --print sends nothing until it gets input. host-bridge queued the prompt forever, waiting for a hello that only comes after the prompt. commit 1161505 — startHandshake now marks the session ready immediately and lets the queued prompt flush.
The field-name mismatch translateOutbound emitted claude's text under a key called event, but the talk CLI reads a key called assistantMessageEvent. The text was produced, handed over, and silently dropped on the floor. a one-word fix in the codex-harness host-bridge rework: event → assistantMessageEvent.
🤓
Technical Stuff

The third bug is the subtle one. From the outside it looked like "claude --print --input-format stream-json exits 0 with no output." But claude was not silent — it was streaming text the whole time. host-bridge was catching that text and filing it under a field name the talk CLI doesn't read. "No output" never meant "claude produced nothing." It meant "claude produced plenty, and we threw it away in translation."

That's why the bug looked unsolvable in the moment: it was diagnosed as a claude-side mystery ("exits silent, root cause not isolated") when it was actually a one-word typo in a host-bridge function two steps away. The fix wasn't hard. It was just hard to see from where people were looking.

Chapter 3: Why It Still Looks Open

In This Chapter
  • The one document still saying "broken"
  • A commit message is a photograph, not a status board

So if the bug is dead, why was it still on the "to do" list? Because of exactly one artifact: the commit message on 1161505, titled "host-bridge: fix claude-code handshake deadlock; flag the talk bug." Its body says: "talk still doesn't work… STATUS/BOARD now carry this honestly as the open Phase 3 gap."

At the instant that commit was written, every word of that was true. The deadlock was fixed; the field-name bug was not yet found; talk did not work. Then the codex-harness work reworked host-bridge, and somewhere in that rework the event → assistantMessageEvent field name got corrected. Talk started working. STATUS.md and BOARD.md were updated to match. The commit message could not be — commit messages are frozen the moment they're written.

⚠️
Warning

A commit message is a photograph of one moment. It is the least reliable place to learn whether something currently works, precisely because it's the one record that can never be corrected. To know the truth: read the code, read the status files, or just run the thing. This explainer exists because someone trusted 1161505's message and repeated "the talk bug is the headline gap" three times without once running cells talk.

💡
Tip

The one cheap thing worth doing: a single line in BOARD.md next to BR.3.5 — "the 1161505 commit message is stale; talk verified working 2026-05-15 on claudia and a fresh birth." Costs nothing, and it stops the next person from re-opening a closed bug.

Part IIThe Capacity Wall (The One That's Real)

Chapter 4: What Walled the Re-Bake

In This Chapter
  • The pool target, and the CPU arithmetic behind it
  • Why the 9th bake timed out
  • The number that was set without looking at the box

The pool keeps a stash of warm, pre-baked eggs so births are instant. How many? A constant: V1_POOL_TARGET_DEPTH = 10 — keep ten warm eggs on hand.

On 2026-05-15 the pool got re-baked: drain the eight stale eggs, bake ten fresh ones. It got eight. The ninth bake timed out. Here's the arithmetic:

  • Every well (VM) is configured with 4 virtual CPUs.
  • The Mac running them has roughly 10–12 physical cores.
  • After the drain there were 4 live cells. Eight successful bakes brought the box to 12 wells. The ninth create — the 13th well — was one VM too many.
  • Under that load a fresh VM boots slowly, sshd comes up late, and wells's "is SSH ready yet?" gate fires before the guest is reachable. TimeoutError.
🧵
Remember

This is a CPU story, not a RAM story — memory was fine the whole time (~4.3 GB across 13 VMs, the wells team measured it). Fourteen VMs × 4 vCPU on a ~12-core box is a 4–5× CPU oversubscription. Reason about cores, not gigabytes.

Now the uncomfortable part. V1_POOL_TARGET_DEPTH is 10 — and that's ten warm eggs, sitting on top of however many cells are live. Ten warm + four live = fourteen wells. The box tops out around twelve or thirteen. The target was set without the live cells in the equation. It was never going to fit, and the re-bake is just the first time the fleet was big enough to prove it.

Chapter 5: Two Halves — Wells's and Cells's

In This Chapter
  • The boot stampede vs. the standing load — two different problems
  • Why both halves are needed, and who owns which

"The bake timed out" is actually hiding two distinct problems, and they belong to two different teams.

The boot stampede — wells's halfThe standing load — cells's half
What it is Ten creates fired as fast as the event loop allows, all booting at once, every fresh VM fighting the others for cores. Even paced one at a time, fourteen wells at rest is more than the box comfortably runs.
The fix Wells's "Admission Control" proposal — a semaphore that paces boots: N at a time, the rest wait their turn instead of failing. See wells-admission-control-for-dummies.html. Cells picks a pool target the box can physically hold — counting the live cells, not just the warm eggs.
🧵
Remember

The wells doc says this itself, in its Part of Tens: "A genuinely undersized host — admission control just makes the wait honest. It paces; it doesn't conjure cores." That sentence is the cells-side gap. Admission control is necessary and not sufficient. It stops the stampede; it does not reduce how many VMs end up running. Cells still has to not ask for more total VMs than fit.

The two halves compose — they don't compete. Wells decides how fast the box can absorb boots. Cells decides how many wells to want in the first place. Neither team's logic has to know about the other's.

Chapter 6: The Cells-Side Options

In This Chapter
  • Four ways to size the pool
  • Which one to ship first

Four ways cells can stop asking for more wells than the box holds:

  1. Lower the target. Set V1_POOL_TARGET_DEPTH = 6 instead of 10. Crude, instant, one-line change. Six warm + four live = ten wells, comfortably under the ceiling. The cost: a shallower pool, so a burst of births can drain it before refill catches up.
  2. Make the target total-aware. Target a total well count, not a warm count: "keep total wells ≤ 12." Four live → bake eight warm; eight live → bake four warm. The pool shrinks as the fleet grows — which is exactly right, because live cells are the thing the warm pool exists to become.
  3. Add a cold tier. A warm egg is RAM-resident and burns vCPU. A hibernated ("cold") egg is a stopped VM — it costs almost nothing. A pool of mostly-cold plus a few hot gives real depth without the standing CPU cost. The BOARD already flags this as a V2 idea. The trade-off: waking a cold egg is slower than claiming a warm one.
  4. More cores. A bigger Mac. The substrate vision is "plug-and-play Mac Mini/Studio" — at some point the honest answer to "I want fifty cells" is hardware, not arithmetic. But that's not today's fourteen-wells problem.
💡
Tip

Ship option 1 or 2 first. Option 1 is a one-line constant; option 2 is a small function change — either one kills the wall this week. Option 3 (cold tier) is the right long-term shape but it's real work and deserves its own proposal. Option 4 is real, but it's a purchase, not a patch.

⚠️
Warning

Do not "fix" this by raising wells's SSH-ready timeout. A longer gate just means a saturated box takes even longer to admit it's in trouble — while the half-booted VMs hold real resources the whole time. The gate isn't too short. The box is too full. Fix the busy, not the patience.

Part IIIThe Part of Tens

Chapter 7: Ten Things to Take Away

  1. claude-code talk works. Verified twice — an old cell and a fresh birth. It is not an open bug.
  2. The only thing saying otherwise is commit 1161505's message — and a commit message can't be edited, so it'll say that forever. Don't trust it.
  3. "No output" can mean "output produced, then dropped in translation." It did here — a one-word field-name typo, event vs assistantMessageEvent.
  4. STATUS.md and BOARD.md are the live truth for claude-code talk. They're correct. Trust them over the commit log.
  5. The capacity wall is real: 10 warm eggs + however many live cells is more VMs than a ~12-core Mac runs.
  6. It's a CPU problem, not a memory problem. Reason about cores.
  7. It has two halves: wells paces the boots (admission control), cells sizes the pool. Both are needed.
  8. Admission control doesn't conjure cores — it makes the wait honest. The pool target is still cells's to get right.
  9. The cheapest cells-side fix is one constant: V1_POOL_TARGET_DEPTH. The right one is probably a total-aware target or a cold tier.
  10. Don't raise the SSH timeout to paper over it. Fix the busy, not the patience.

Where to Go From Here

Two loose ends went in. One comes out tied: there is nothing to build for the claude-code talk bug, because there is no claude-code talk bug. The other needs one small, well-shaped decision.

  1. Loose end #1 — close it on paper. Optionally add a line to BOARD.md marking BR.3.5 confirmed-closed, so the stale commit message can't lure anyone back in. That's the entire to-do list for #1.
  2. Loose end #2 — Pete picks a pool-sizing approach. Lower the target, make it total-aware, grow a cold tier, or buy cores. Options 1 and 2 are this-week-sized.
  3. Ship the small one behind the normal branch-and-merge flow — it's a constant or a small function, with the existing pool tests.
  4. If the cold tier is chosen, it gets its own proposal — it's V2-shaped work, not a one-liner.

Loose end #2 is the cells-side companion to wells-admission-control-for-dummies.html. Wells filed its half — pace the boots. This is the cells half — don't ask for more wells than the box can hold. Read them together; they're one problem with a seam down the middle.
