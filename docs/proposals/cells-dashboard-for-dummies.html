The Cheat Sheet

Tear-out card. If you read nothing else in this book, read this.

What it is, in one sentence
A calm, story-first web dashboard for your fleet of cells — a narrator-written read of "who's alive, who's asleep, what they're up to" — served by a cell whose only job is to watch the other cells.
Where it lives
A cell named cells-narrator, hosted by your own wells daemon, reachable at https://cells.cells.md. Sibling URL to wells.cells.md; same Cloudflare push pattern.
What the cell holds
A narrator (the agent that writes the read), a Next.js app, and a self-hosted Convex database — all three inside the same VM, talking over the local network. Cell-only; no external service to deploy.
The three pages
(1) the story — the main glance: a narrator-written read, every cell grouped by state, a one-line pool summary, the "lately" timeline. (2) the pool — the egg pool: members by tier, variant, claim history, age. (3) cell/[name] — vital signs and self-report for a single cell.
What's not here
No talk page. No chat surface. No "do things" controls. The dashboard is purely informational. Killing, sleeping, or birthing cells stays in the cells CLI.
The trigger
A button, not a timer. Each press of Refresh runs one narrator pass; each press of Refresh + wake sleepers wakes every hibernating cell and rolls them in too. No loop, no schedule — the dashboard does its thinking only when you ask.
The line in the sand
Comprehension, not monitoring. No gauges, no metrics walls, no log tails, no time-series charts. Show what happened ("a cell was born," "claude-cell finished its CORA filing"), not what was called.
The boundary
Cells's view of the fleet — births, kills, hibernations, what each agent says it's doing, pool health. Not the substrate. RAM, VZ processes, vmnet leases, image storage — those are the wells dashboard.
The big differentiator
Cells can talk back. Wells has to interpret runtime.json from outside; the cells narrator can just ask each cell "what are you doing right now?" and quote the answer. The dashboard's prose is sourced from the agents themselves, not guessed.
Always-on fallback
A tiny operator-side daemon (the first long-running cells process) reads ~/.cells/cells.json and serves a bare HTML page at /up: "Fleet up · N cells alive, M asleep · last narrator pass: ...". When the narrator cell is asleep, this is what answers.
What's already done
Nothing yet. The wells-dashboard project exists at ~/Projects/wells-dashboard/ as the architectural template. This book is the first plan document for the cells side. The narrator cell, the Convex schema, the Next.js app, the operator-side daemon — all to be built.
What it costs to run idle
≈ nothing. The narrator cell hibernates when the page isn't open. Wake-on-traffic brings it back in ~1s when someone visits cells.cells.md. The fleet's dashboard runs on the fleet's value prop.

Introduction

About This Book

You have a fleet of always-on AI agents living on your own hardware. They have names. Some are awake, some are hibernating, some have been quietly working on a task for hours. You want to know how they're doing — without staring at a wall of log tails or doing math on JSON files.

This book is the plan for a dashboard that tells you. A single page, written by another agent whose only job is to glance at the fleet and tell you the truth in prose. You press a button; it asks the cells how they're doing; it writes you a paragraph; you go on with your day.

We're not building this dashboard yet. This book is the design — the shape, the pages, the data, the small architectural decisions worth getting right before the first commit.

🧵
Remember

This is the cells dashboard — the fleet's view of itself. Cells sees what its agents are doing. The substrate they run on — VMs, host RAM, leases — has its own dashboard at wells.cells.md. Two doors, one for each layer.

Foolish Assumptions

This book assumes you:

  • Know that cells is a fleet of always-on AI agents, each in its own VM, addressable by name. A cells CLI births / talks to / kills / hibernates them; an egg pool keeps warm VMs on hand for fast birth.
  • Know that wells is the substrate underneath — Linux VMs managed by a welld daemon. Wells has its own dashboard for substrate concerns; this is the layer above.
  • Have at least once typed cells list and read the output of cat ~/.cells/cells.json. The state files this dashboard reads are not exotic; they're the same ones the CLI prints.
  • Are not opposed to a dashboard that thinks before it speaks. Even if the agent is occasionally goofy. Especially then.

Part IWhat This Even Is (And Why It's Not Wells's Dashboard)

Chapter 1: The Fleet Glance

In This Chapter
  • The job: tell you how your fleet is doing in five seconds
  • Why "fleet" is the noun, not "agent" or "VM"
  • The five-second read vs the half-hour audit

Cells gives you a fleet. Maybe four agents today, maybe a dozen next month, maybe fifty when the substrate is genuinely doing its job. Each one is a small persistent AI living in its own little Linux box, with its own name and its own work. Some are busy; some are asleep; one finished a long task an hour ago and is just sitting there.

The dashboard's job is to tell you the state of all that, at a glance. Who's alive. Who's asleep. What they say they're up to. What changed since last time you looked. One paragraph at the top of the page, written by another agent that asked the others how they're doing.

🧵
Remember

Fleet is the noun. Not "an agent." Not "a VM." The dashboard's unit of attention is the whole fleet at once. Individual cells are a drill-down, not the front door.

Chapter 2: Not the Wells Dashboard

You already have a dashboard at wells.cells.md — the wells team built it first, on the same architectural pattern this one will follow. The temptation is to shrug and say "great, we're done, the wells dashboard already shows us the boxes." It shows you the boxes. It does not show you the agents inside them.

That distinction is the entire reason this book exists. Wells's dashboard, by design, refuses to peek inside a well. It reports the membrane: a VM was born, a VM is hibernating, a VM is holding 1 GB of RAM. It cannot tell you that cora-file finished its CORA filing twelve minutes ago, because that's a thing only the agent inside the VM knows.

The wells dashboard shows…The cells dashboard shows…
VM lifecycle (born / running / hibernating / stopped) Cell lifecycle (born / alive / hibernating / killed) plus what each cell is doing
Host RAM, per-VM memory, the Mac's headroom Pool health: tiers, ages, claim history, variant signatures
The image library and where each VM was forged from Per-cell DNA: harness, model chain, hatched-from-egg, lineage
Substrate health (welld up? leases sane?) Fleet activity: births, kills, hibernates, recent self-reports
"A VM was sealed in 3.8s" "tax-filing-2025 is mid-step on form 1040 Schedule C"
🧵
Remember

Wells sees vital signs; cells has the patient's chart. Wells says "the patient is breathing, heart rate normal, holding fluids." Cells says "the patient is reading Chapter 7 and just took a sip of coffee." Same patient, two honest views.

Sidebar — Why not one combined dashboard

You might wish the two dashboards were merged: one URL, two tabs, done. They're not, for two reasons. First, the wells/cells boundary was hard-won and we should not collapse it in the UI just because it's geographically tempting. Second, the two narrators have different jobs: the wells narrator interprets JSON about boxes; the cells narrator asks agents what they're doing. Different work, different prompts, different cadence. Sibling cells, sibling URLs.

Chapter 3: Why a Button, Not a Loop

In This Chapter
  • The wells dashboard uses a timer; this one uses a button
  • Why the button is the honest interface
  • What "lately" means when there's no schedule

The wells dashboard runs a narrator loop on a timer — every few minutes it wakes up, asks welld for facts, writes a new read. That makes sense for the substrate: things are happening at the substrate level all the time, and a periodic "tell me what's going on" is exactly the right cadence.

The cells dashboard does it differently. Each press of a button runs exactly one narrator pass. There is no loop. There is no schedule. If you don't open the dashboard for a week, the narrator does no work for a week. When you do, you press Refresh, the narrator wakes, asks the fleet how things are going, writes a fresh paragraph, and goes back to sleep.

💡
Tip

This isn't laziness; it's honesty. Each cell roll-call costs real LLM tokens. Running a periodic loop you don't read is paying to write paragraphs nobody sees. The button makes the cost visible: every read you get is one you actually asked for.

"Lately" — the timeline of recent events at the bottom of the page — works the same way. Each press diffs against the previous snapshot in Convex. If you press every five minutes, lately is the last five minutes. If you press once a day, lately is the day, compressed. The dashboard's clock is your attention, not a wall clock.

⚠️
Warning

One real trade-off: between two button presses, fast events can vanish. If a cell is born and killed between presses, the lately diff sees no net change. That's the price of not running a tailer. We'll know whether it matters the first week — if it does, a small always-on event tailer is the fix.

Chapter 4: The Trick — Cells Can Talk Back

The cells dashboard has one thing the wells dashboard fundamentally cannot have: its subjects can answer questions about themselves.

Wells writes prose by reading JSON. runtime.json says "running"; the narrator says "running." lease_count is 178; the narrator says "178 orphan leases." It's interpretation, but it's all from the outside. There's no way for a VM to tell wells what it's up to — VMs don't have opinions.

Cells's subjects do. The narrator can run cells talk pi-cell "give me a one-line status of what you're doing" against any alive cell and get back something like:

Mid-way through reading the wells dashboard mockup HTML to extract the visual tokens; about to write them into the cells dashboard CSS file. — pi-cell, asked at 10:14 AM

That sentence didn't exist anywhere on disk a second ago. The narrator asked, and the agent answered — in its own voice, knowing its own context. The dashboard's "read" becomes a synthesis of those answers, not an interpretive guess.

🧵
Remember

The narrator is a manager, not a biographer. Wells's narrator watches and interprets. Cells's narrator asks and synthesizes. That changes the whole tone: less "I'm reporting on you" and more "I checked in with everyone."

Part IIThe Stack Behind the Glass

Chapter 5: A Cell Named cells-narrator

In This Chapter
  • The narrator is a cell, like every other cell
  • Same harness as the wells narrator — same playbook
  • Why putting the cells dashboard on a cell is the right kind of recursive

The dashboard lives in a cell named cells-narrator. Pi harness, same as the wells narrator — we already have a working template at ~/Projects/wells-dashboard/ to copy from. Birth it from the warm-egg pool, give it the project directory with the Next.js app and Convex deployment, point Cloudflare at it.

This means the cells dashboard is itself a member of the fleet it's watching. It shows up in its own portrait. When you press Refresh and the narrator wakes up to do a pass, the page will, with appropriate honesty, list a sleeping cell named cells-narrator in the "asleep" group, which is itself, which is fine.

💡
Tip

The recursion isn't a stunt — it's the cleanest deployment. If a Next.js dashboard can't run on a cell, that's a cells bug worth fixing. The dashboard proves out the platform every time you load it.

Chapter 6: The Cast

Here's everyone who shows up to work:

Technical Stuff

The narrator is a Pi agent in print mode (pi -p) or driven via Pi's SDK from a Next.js server route. There is no RPC mode and no pi-web-ui — those were needed for the wells dashboard's talk page, which we're not building. Drop them from the dependency footprint.

Chapter 7: The Operator Daemon — The Bare Truth Path

The cells operator daemon is the first long-running cells-side process. The cells CLI today is invocation-based: you type cells list and it reads files and exits. Nothing keeps running. For the dashboard, we need something that does.

The daemon does two things:

  1. Serves /up — a bare HTML page (no agent, no Convex, no JavaScript) that reads ~/.cells/cells.json and pool.json and renders: "Fleet up · 4 cells alive, 2 asleep, 0 dead · pool: 8 eggs, 3 claimed · last narrator read: 24 minutes ago." This is what answers when the rich app is asleep.
  2. (Optional) Tails events into Convex — watches ~/.cells/logs/ and writes structured event rows to Convex whenever a birth, kill, or hibernation happens. Closes the lately-between-presses gap if we decide we care. Cuttable from V1.
⚠️
Warning

The daemon needs to keep working when the cells repo is moving underneath it. Install it as a launchd plist with a stable command (cells daemon or similar), not a hardcoded path to ~/Projects/cells/bin/.... Path renames have bitten us before.

Sidebar — Why not use welld's degradation path

The wells dashboard relies on welld serving /up when its cell is asleep — welld is already always-on, so it gets the job for free. Cells has no equivalent always-on daemon today. We could plumb the cells /up through welld and let welld serve a static page on cells's behalf — but that collapses the boundary on a technicality. Cleaner: cells gets its own tiny daemon, even if its only initial job is serving thirty lines of HTML.

Part IIIThe Data Underneath

Chapter 8: What the Narrator Reads

In This Chapter
  • Cells has no daemon like welld — the facts live in files
  • What's in ~/.cells/ and what each file means
  • The state-files-as-API pattern

Wells has welld, which exposes facts over HTTP. Cells has ~/.cells/, which exposes facts over JSON files. The narrator just reads them. Here's the menu:

FileWhat it holds
~/.cells/cells.json The fleet: every cell's name, status, harness, model chain, hatched-from-egg, created_at. The "who exists" answer.
~/.cells/pool.json The egg pool: members with id, well_name, variant_signature, state (live/asleep), tier, born_at, claimed_at, claimed_by, max_age_at.
~/.cells/channels.json Comm channels between cells. (Used today for very little; future: the dashboard could surface inter-cell talk.)
~/.cells/pulse.json Pulse system state. Not on the V1 page; here for completeness.
~/.cells/logs/ Per-event transcripts: every birth, kill, talk. Big, append-only, useful for "lately" and per-cell drill-downs.
🤓
Technical Stuff

For the narrator to read these files, they need to be reachable from inside the narrator cell. Options: (a) the operator daemon serves them over HTTP on the host's LAN address, (b) a one-way push: the daemon writes them into a shared state path the cell mounts, (c) the narrator SSHes to the host. (a) is the cleanest mirror of how wells does it; (c) is the cheapest to start. Decide at build time.

Chapter 9: The Roll-Call

Reading state files tells the narrator who exists. Asking each cell tells the narrator what they're doing. The roll-call is the second of those, and it's where the cells dashboard earns its keep.

For each alive cell on the press, the narrator does this:

  1. Ask — cells talk <name> "<status prompt>". A fixed, short prompt the narrator uses every time: "In one sentence, what are you working on right now, and how's it going?"
  2. Capture — write the answer into Convex, attributed and timestamped.
  3. Synthesize — once every cell has reported, the narrator writes the read using those quotes as primary sources. "claude-cell finished its CORA filing 12 minutes ago; pi-cell is mid-way through reading the dashboard spec…"
💡
Tip

Keep the status prompt fixed and short. The narrator's voice goes in the synthesis step, not in the question. If you let the narrator improvise the prompt, you'll get inconsistent answers across cells and lose the ability to compare them.

⚠️
Warning

The roll-call is the slow part. Asking N cells in series at 1–2 seconds each means a 10-cell fleet takes ~10–20 seconds per Refresh. Run the roll-call calls in parallel; the button still feels slow with a big fleet. Show loading state honestly — "asking pi-cell… asking claude-cell…" — not a fake-looking spinner.

Chapter 10: The Convex Schema

Convex is the system of record. Every roll-call answer, every narrator read, every birth/kill/talk that the operator daemon tails — they all go here. The pages then subscribe with useQuery and update live. 

// convex/schema.ts — shape, not the final source

snapshots         // one row per narrator press: the timeline
  pressed_at, raw_state_json, cell_count, alive, asleep, dead,
  pool_size, woke_sleepers   // true if user pressed the power button

reads             // the narrator's prose, one per press
  written_at, body, based_on_snapshot

cells             // current known cells (upserted each press)
  name, harness, model_chain, hatched_from_egg, well_name,
  created_at, status, last_seen_alive_at, last_self_report

cell_self_reports // every roll-call answer, kept
  cell_name, asked_at, prompt, answer, snapshot_id

cell_timeline     // per-cell lifecycle events
  cell_name, occurred_at, kind, summary

pool_members      // upserted from pool.json each press
  id, well_name, variant_signature, state, tier,
  born_at, claimed_at, claimed_by, max_age_at

events            // the "lately" timeline, narrated
  occurred_at, kind, summary, cell_name?, snapshot_id

transcripts       // (optional, tailed by operator daemon)
  kind, cell_name, occurred_at, content
🧵
Remember

Convex is the system of record for what was said. The filesystem is authoritative for "who exists right now," but for "what did the fleet say it was doing two days ago," the dashboard's Convex is where you go. That's a real change from how cells works today.

Chapter 11: One Press, End to End

Here's what happens when you click Refresh:

  1. Browser → Next.js — POST /api/refresh on the cell.
  2. Next.js → narrator — server route invokes the narrator agent in print mode (or via the Pi SDK).
  3. Narrator reads state — pulls cells.json, pool.json, the recent log files. Diffs against the last snapshot in Convex.
  4. Roll-call — for each alive cell, cells talk <name> in parallel. Each answer is written to Convex as it arrives; the page sees them populate live via useQuery.
  5. Narrator writes the read — one Pi pass synthesizes the quotes plus the diff into a paragraph or two of prose. Writes it to reads in Convex.
  6. Narrator writes events — any state changes since the last snapshot get written to events: "egg-833480 was claimed by pi-cell," "cora-file was killed," etc.
  7. Browser sees it all — the page is already subscribed; the new read, reports, and events render without a page refresh.
  8. Cell goes back to sleep — until the next press, or wells's auto-sleep timer expires.

Chapter 15: The Narrator's Voice

In This Chapter
  • What "voice" means when an agent is writing UI copy
  • The cells voice rules — and how they differ from wells's
  • Why the narrator never says "I'm a Pi agent"

The narrator's SYSTEM.md carries the voice rules. The key ones:

  • Plain English. "Four cells are alive," not "cells.alive_count === 4." If the read could be paraphrased from prose into UI in two seconds, the prose was right.
  • Operational first. Lead with the state of the world; trailing detail is fine. "Four cells alive…" before "claude-cell said it just sealed its first checkpoint."
  • Quote, don't summarize. When a cell self-reports, prefer quoting their wording over paraphrasing it. The whole reason we asked is to get the agent's voice — squashing it back into the narrator's is wasteful.
  • Cells are cells. Never reference the harness ("the Pi agent…"), model ("running on gpt-5.5…"), or provider ("via Anthropic…") in the user-facing read. Those are internal details that belong on the drill-down page, not the front door.
  • Flag warts calmly. "Worth a glance" is a tone, not a category. "One cell hasn't answered in 12 hours — probably fine, but you might check on it" is cells's flag voice; "ALERT: CELL UNRESPONSIVE" is not.
🧵
Remember

The narrator is part of the fleet's voice. When it writes about the fleet, it writes from the fleet's point of view, not from "I, a Pi agent, observe the following cells." The user has a fleet of cells; the dashboard is cells talking about cells.

Chapter 16: The Two Buttons

There are exactly two buttons on the dashboard, and they live next to each other:

ButtonWhat it doesWhen you'd use it
Refresh (primary) One narrator pass. Asks the alive cells, skips the asleep ones. Reports sleepers from Convex history ("cora-file hibernated 27m ago after finishing X"). Default. The button you'll press 95% of the time.
Refresh + wake sleepers Wakes every hibernating cell, asks them, lets them go back to sleep. Same narrator pass, just with a wider roll-call. When you want everyone to chime in — debugging, weekly review, "wait what was tax-2025 doing yesterday."
💡
Tip

Show the wake count up front: "this will wake 2 sleepers (~2s)". Pete can decide if it's worth it; the cheap default is one click away.

Chapter 17: When Sleepers Stay Asleep

On a default Refresh, the narrator does not wake sleepers. This is a real product decision, not laziness. Sleepers report from their last known state — Convex remembers what they were doing when they went to sleep, plus the exact wording of their last self-report. The dashboard says:

cora-file hibernated 27 minutes ago after finishing its CORA filing. Last self-report: "Drafted the request, attached the PDF, and queued the Gmail draft for you to review." — from history, not asked today

That's honest — the dashboard tells you the last thing the cell said, dated to when it said it. If you want fresh, you press the wake button. If you don't, you get the freshest non-disruptive answer.

⚠️
Warning

Waking sleepers costs real money — every wake is an LLM token call (one per cell) plus the cell's own wake latency. A fleet of fifty sleepers is fifty model calls in a row. Make sure the dashboard surfaces a count before the click, not after the bill.

Chapter 18: The Bare /up Path

When the narrator cell is asleep — and at idle, that's most of the time — the rich dashboard isn't reachable. The browser-to-cell handshake won't fire because Cloudflare can't reach a hibernating well's IP. The fallback is the operator daemon, serving /up directly on the Mac.

/up is bare HTML. No JavaScript, no Convex, no agent. Reads ~/.cells/cells.json at request time, renders a paragraph: 

Cells fleet — up.

4 cells alive, 2 asleep, 0 dead. Pool: 11/13 in use, 2 free.
Last narrator read: 24 minutes ago.

Alive:    claude-cell, codex-cell, pi-cell, wells
Asleep:   cora-file, tax-2025
Dead:     —

The rich dashboard at https://cells.cells.md will boot in ~1s when you visit.
🧵
Remember

If you ever see /up, the dashboard cell is asleep. That's a feature, not a failure — it means the system is doing exactly what we want, hibernating when nobody's looking. Visiting cells.cells.md directly will wake it.

Part VIThe Part of Tens

Ten Things This Dashboard Refuses to Show

  1. CPU/memory graphs. Substrate-side concerns — go to wells.cells.md.
  2. Time-series anything. The dashboard's time horizon is "now, plus lately." History lives in Convex for the narrator to consult, not for you to squint at.
  3. The cells's internal session transcripts. What an agent says to itself is its business; we show what it tells us about itself, no more.
  4. Tool-call counts. Five cells averaging eleven tool calls per turn is not a load-bearing fact. The narrator can mention them when they matter; we don't graph them.
  5. Model attribution in the read. Cells are cells; "running on gpt-5.5" is a drill-down detail, not front-door copy.
  6. Cost rollups. Daily spend is a separate concern with its own honest place — not a number on the front door distracting you from the fleet.
  7. "Health scores" or made-up percentages. No fleet-health-is-87% gauges. Either everything's fine, or something specific needs a glance, named and dated.
  8. A chat with the narrator. No talk page. The narrator writes; it does not converse.
  9. Birth/kill buttons. No "do things" controls. Lifecycle stays in the CLI, where it belongs.
  10. Anything that requires interpretation by you. If you have to read a number and decide what it means, the narrator failed. Make the narrator try again.

Ten Reads You Might See

What the read looks like in different fleet states. The narrator's job is to make each of these natural to read at a glance:

  1. Quiet. "Three cells alive, all idle. Nothing's happened in two hours."
  2. Busy. "Five cells alive, four mid-task. claude-cell is on Schedule C, codex-cell is sweeping a benchmark, pi-cell is reading the wells docs, wells is writing release notes."
  3. Catastrophic. "One cell alive (the narrator). Five expected. ~/.cells/cells.json still lists them — they're not reachable. Wells dashboard shows them as hibernating, but they're not waking."
  4. Half-asleep. "Two cells awake, six hibernating. Press Refresh + wake sleepers if you want everyone to chime in (~6s)."
  5. Mid-eval. "Two cells alive, both running birth-eval passes for harden-birth. claude-cell is on row 14, codex-cell is on row 11. Pool's healthy."
  6. Stale. "Four cells alive — all answered, but pi-cell's report is the same as last hour ('reading the wells docs'). Either it's deep in something or it's stuck. Worth a glance."
  7. Fresh. "Two newborns: claude-cell and codex-cell both came up in the last ten minutes. claude-cell sealed its first checkpoint already."
  8. Dying. "Three cells alive, one stuck in the death-hibernate seam — tax-2025 has shown 'shutting down' for 14 minutes. Probably hung on the kill. cells kill --force tax-2025 when you have a moment."
  9. Empty. "No cells. Pool has 13 warm eggs ready. cells birth when you're ready."
  10. Recursive. "Five cells alive, including me — cells-narrator. I'm awake because you're reading this. I'll go back to sleep when you close the tab."

Where to Go From Here

This book lays out the shape. The actual build is, roughly, in this order:

  1. The operator daemon — small, always-on, serves /up from ~/.cells/cells.json. Install as a launchd plist. Stable command, no hardcoded repo paths. This is the foundation everything else assumes is there.
  2. The cell cells-narrator — birth it from the warm-egg pool, Pi harness, copy the scaffold from ~/Projects/wells-dashboard/. Point Cloudflare at it; confirm cells.cells.md resolves.
  3. Convex on the cell — port the wells-dashboard docker-compose.yml and admin-key bootstrap; deploy the cells schema (Chapter 10).
  4. The narrator function — one Pi pass: read state, roll-call alive cells, write to Convex. Just the function — no Next.js wiring yet. Verify it works from the cell's shell.
  5. The Next.js app — the story page first (with the two buttons). Live data via useQuery. Then the pool page. Then cell/[name].
  6. The visual polish — match the mockups in this book. Reuse the token set from wells's dashboard-mock/style.css where it makes sense; tweak the accent to cells's olive-green so the sibling relationship reads.
  7. The optional event tailer — operator daemon tails birth/kill/talk events into Convex's events table. Skip if "lately as press-diff" is good enough.
