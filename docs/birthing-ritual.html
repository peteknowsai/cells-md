The Birthing Ritual

How mother turns a claimed generic egg into a configured, live cell.

This is the design contract for every cells birth. Three phases, in order — bake the egg, prove the brain, run the post-birth tail. The cell is declared alive after the brain proof; the tail lands behind the declaration. Reliability over speed: never put an external service (Cloudflare, Slack, the well checkpoint) in the critical path.

Live implementation: dna/specials/mother/.claude/skills/birth/SKILL.md is the canonical short-form ritual the claude-code mother runs. Two Mac-side scripts do the heavy lifting: scripts/imprint-cell.sh (phase 1) and scripts/birth-postwork.sh (phase 3). The phases below describe the logical contract; the script source is the authority on what each one actually executes.

What you're handed

When birth begins, mother is given three things:

Cell name
The name the new cell will answer to — e.g. bob.
Egg
The well name of a claimed generic egg from the pool. Already running, already loaded. This is your starting material — you don't create it.
Config blob
JSON describing how this cell should be configured (below).

What's already on the egg

The egg is generic and maximally pre-loaded. You do not install anything during birth — everything that can be baked ahead of time already is. Your job is to imprint identity, switch on what this cell needs, and wire its external surfaces.

Eggs are kept fresh — re-baked periodically so the toolchain, pi, and packages stay current. Trust that the egg is recent; you never need to update or install anything on it.

The three phases

Mother runs three phases in order, per harness. The first two block; the third is backgrounded and observed via ~/.cells/postwork/<name>.json. The harness comes from the blob; everything else differs only in which CLI gets pinged for the brain proof.

Phase 1 · Bake the egg (synchronous)

One Mac-side script — scripts/imprint-cell.sh — does every per-cell mutation on the egg: identity substitution, model + thinking + provider + chain, tmux color, status file, extension registration, optional-package toggling, harness-specific config (Anthropic patches, codex / hermes provider keys, claude-code __NAME__ in CLAUDE.md). The blob feeds it directly; no per-harness orchestration code on the mother side.

# on the Mac, from the cells repo
bash scripts/imprint-cell.sh <egg-well> <name> '<blob-json>'

Output ends with BAKE-OK. Anything else is a failure — skip to Failure. See what imprint-cell.sh does internally for the per-substitution detail (useful when debugging the script, not part of mother's job).

Phase 2 · Prove the brain (synchronous)

One well_exec per harness. Each runs the harness's --print-style one-shot mode against a fixed prompt and checks for the harness's success marker on stdout. The cell stays in this phase until the brain answers; if it never answers, birth fails and the egg gets swept.

HarnessEnd-test command (run on the egg as root, HOME=/root)Marker
pitimeout 30 pi --print "say ok"PI-OK
claude-codetimeout 60 claude --print "say ok"CLAUDE-OK
codextimeout 120 codex exec --skip-git-repo-check --dangerously-bypass-approvals-and-sandbox "say ok" </dev/nullCODEX-OK
hermestimeout 120 hermes -z "say ok"HERMES-OK

All four are wrapped in sudo bash -lc 'export HOME=/root; cd /root && source /etc/profile.d/cells-env.sh && ...' — without sudo + HOME=/root the harness reads /home/well/.config and tests the wrong tree. The exact incantation is in SKILL.md.

The brain proof is the only sync gate after bake. Site-serves, Worker liveness, channel binding, identity-substitution residue checks — anything that isn't "is this cell's CLI actually answering through the proxy" — are observed asynchronously in phase 3.

Phase 3 · Run the post-birth tail (asynchronous)

Mother nohups scripts/birth-postwork.sh and immediately writes the alive outcome to $CELL_OUTCOME_FILE. The script runs the steps that don't need to gate "cell is alive" and writes per-step status to ~/.cells/postwork/<name>.json as it goes, so a failure in any one step is visible (cells doctor, cells list, the dashboard) without anyone having to tail a log file.

# on the Mac
POSTLOG="$HOME/.cells/logs/birth-postwork/<name>.log"
mkdir -p "$(dirname "$POSTLOG")"
nohup bash "${CELLS_REPO:-$HOME/Projects/cells}/scripts/birth-postwork.sh" \
  "<name>" "<egg-well>" '<blob-json>' > "$POSTLOG" 2>&1 &
disown

The steps it runs, in order: site service registration, well URL flipped public, Cloudflare Worker deploy, channel binding (Slack / email per the blob), harness update, well checkpoint. None of them block birth declaration. Detail: what birth-postwork.sh does internally.

Declare + record

After phase 2 passes and phase 3 is nohup'd:

  1. Write {"success":true,"message":"cell <name> alive · <model> (post-birth async)"} to $CELL_OUTCOME_FILE.
  2. Tell the user exactly one line: "Cell <name> is alive. Talk to it with cells talk <name>." No caveats.

The CLI's birth completion handler reads the outcome file, registers the cell as alive, and returns control to whoever called cells birth. Phase 3 is still running at that point; cells doctor and the dashboard will surface any failed step from postwork.json.

Failure

Phase 1 fails (no BAKE-OK) or phase 2 fails (no *-OK marker within the timeout):

echo '{"success":false,"message":"phase <N>: <one-line reason>"}' > "$CELL_OUTCOME_FILE"

Stop. The CLI sweeps the egg on a failed outcome; a fresh egg is faster than salvaging a half-baked one.

Phase 3 failures (worker didn't deploy, channels didn't bind) are not birth failures — the cell is alive and usable. They surface as a postwork.json status of failed:<step>, and cells doctor flags them.

Appendix · What imprint-cell.sh does internally

The detail below is for debugging scripts/imprint-cell.sh, not part of mother's job. The script is the authoritative source; this section is a reading guide.

1 · Imprint identity (every harness)

The cell learns its name. __NAME__ substituted across the DNA and the tmux color chip. For claude-code, CLAUDE.md is in the substitution set (it's the entrypoint the claude CLI auto-loads from cwd).

# on the egg
sed -i 's/__NAME__/<name>/g' \
  /root/AGENTS.md /root/SOUL.md /root/IDENTITY.md \
  /root/CELLS.md /root/CONTACTS.md /root/HEARTBEAT.md /root/package.json \
  ${HARNESS_CLAUDE_CODE:+/root/CLAUDE.md}

# on the Mac: compute the cell's color, then substitute on the egg
read CBG CFG < <(bash scripts/cell-color.sh <name>)
sed -i "s|__CELL_BG__|$CBG|g; s|__CELL_FG__|$CFG|g; s|__NAME__|<name>|g" /root/.tmux.conf

2 · Apply model config (per harness)

The cell's brain is configured from the blob's model, provider, thinking, and chain. Which file gets touched depends on the harness; imprint-cell.sh routes accordingly.

# pi — settings.json carries model + provider + thinking + chain
sed -i 's/__MODEL__/<model>/g'        /root/.pi/settings.json
sed -i 's/__PROVIDER__/<provider>/g'  /root/.pi/settings.json
sed -i 's/__THINKING__/<thinking>/g'  /root/.pi/settings.json
# chain: the DNA placeholder is a quoted string ("__MODEL_CHAIN__") so the
# file stays valid JSON — sed swaps the quoted token for a bare JSON array.
# Use | as the delimiter (chain entries contain /).
sed -i 's|"__MODEL_CHAIN__"|<chain-json>|g' /root/.pi/settings.json

# validate — pi crash-loops on a malformed settings.json
jq . /root/.pi/settings.json > /dev/null

If the blob's provider is anthropic — a pi cell on an Anthropic model — the cell must reach api.anthropic.com directly with its ANTHROPIC_API_KEY, not through the subscriptions proxy (pi-via-Max is fingerprint-blocked; the paid key is clean). Drop the routing flag and re-run the pi patches so the Anthropic baseUrl is restored to direct:

# on the egg — ONLY when the blob's provider is "anthropic"
touch /root/.anthropic-direct
sudo bash /root/scripts/apply-pi-patches.sh

3 · Write the status file (every harness)

The tmux bar reads this. Channels start empty — phase 3's channels_bind step fills them in the pi case, no-ops elsewhere.

# on the egg
mkdir -p /root/.pi
echo '{"harness":"<harness>","channels":[]}' > /root/.pi/status.json

4 · Switch on extensions (pi only)

All four in-tree extensions are already on disk. Register only the ones in the blob's extensions — the rest stay on disk, switched off. Do not delete the unused ones. If extensions is empty, or the harness isn't pi, this is a no-op.

# on the egg, for each <ext> in the blob's extensions array
jq --arg p ".pi/extensions/<ext>/index.ts" \
  'if (.extensions | index($p)) then . else .extensions += [$p] end' \
  /root/.pi/settings.json > /tmp/s.json && mv /tmp/s.json /root/.pi/settings.json

Appendix · What birth-postwork.sh does internally

The post-birth script runs each step through a run_step wrapper that captures output, records ok/failed + ISO timestamp + a tail of the failure detail to ~/.cells/postwork/<name>.json, and continues regardless. No step is gated on the previous one finishing — worker deploy doesn't wait on Slack, harness update doesn't wait on the worker. Order is just a stable execution sequence, not a dependency chain.

  1. site_service — scripts/register-site-service.sh <name> <egg-well>. Re-registers well-site.service with the right CELL_NAME so the cell's port-8080 server starts on boot.
  2. well_url_public — well url update --auth public -s <egg-well>. Flips the egg's well URL public so the front-door worker can route <name>.cells.md traffic.
  3. worker_deploy — scripts/deploy-cell-worker.sh <name> <egg-well>. Renders the per-cell Cloudflare Worker template and runs wrangler deploy.
  4. channels_bind — scripts/bind-cell-channels.sh <name> <blob>. For pi cells with channels set: creates the Slack channel + binds it + updates /root/.pi/status.json. No-op for claude-code / codex / hermes.
  5. harness_update — scripts/update-cell-harness.sh <egg-well> <blob>. Brings the in-cell harness binary up to current — eggs drift between bakes; this re-installs the latest of whichever harness the blob selected.
  6. checkpoint — well checkpoint create -s <egg-well> --comment "born-<name>". Final clean restore point. Stamps completed_at on postwork.json.

Per-harness notes

The three phases are the same for every harness. Differences are confined to phase 2 (the brain-proof CLI invocation, in the table above) and what imprint-cell.sh writes during phase 1.

claude-code
Phase 1 writes model + effortLevel into /root/.claude/settings.json and substitutes __NAME__ in CLAUDE.md (the entrypoint the claude CLI auto-loads from cwd, counterpart to pi's AGENTS.md). Extensions, packages, and cells-side channels don't apply — the claude CLI carries its own agent surface. Phase 2 hits claude --print "say ok" through the proxy (Max subscription token swap happens proxy-side). Phase 3 is the same script as everyone else, minus channel binding.
codex
Phase 1 writes model + model_reasoning_effort into /root/.codex/config.toml and puts __NAME__ in the provider's http_headers (the x-cell-name the proxy logs). The [model_providers.cells] block already points at proxy.cells.md/codex with env_key = "OPENAI_CODEX_API_KEY" — the env shim exports that to CELLS_PROXY_SECRET; the proxy swaps it for the real ChatGPT token. Phase 2 hits codex exec with the bypass flags. Phase 3: same script, no channel binding.
hermes
Phase 1 writes model.default + agent.reasoning_effort into /root/.hermes/config.yaml and symlinks /root/SOUL.md → $HERMES_HOME/SOUL.md so hermes loads the cell's persona. The providers.cells block points hermes at proxy.cells.md/codex via OPENAI_CODEX_API_KEY — same path codex uses. hermes is not a coding machine; cells doesn't stack extensions / packages / channels onto it (its capability stack comes from hermes itself). Phase 2 hits hermes -z "say ok". Phase 3: same script, no channel binding. Full background in docs/proposals/hermes-harness.html.
pi
Phase 1 writes model + provider + thinking + chain into /root/.pi/settings.json, registers any blob-requested extensions (memory, mentality, wiki, dream), and toggles optional packages (pi-web-access, …). When provider is anthropic, imprint-cell.sh also drops /root/.anthropic-direct and applies the proxy patches. Phase 2 hits pi --print "say ok". Phase 3 is the only branch where channels_bind actually does work (pi cells get Slack / email surfaces via cells-side channels).

The legacy anchors #codex-branch and #hermes-branch resolve here too, for any docs / chat links that already point at them.
