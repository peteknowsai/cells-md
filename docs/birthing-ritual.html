The Birthing Ritual

How mother turns a claimed generic egg into a configured, live cell.

This is the ritual mother follows for every cells birth. Work top to bottom — each step gates the next. Don't improvise the order. Birth isn't a race; it's done when the cell is proven working (step 8).

What you're handed

When birth begins, mother is given three things:

Cell name
The name the new cell will answer to — e.g. bob.
Egg
The well name of a claimed generic egg from the pool. Already running, already loaded. This is your starting material — you don't create it.
Config blob
JSON describing how this cell should be configured (below).

The config blob

What's already on the egg

The egg is generic and maximally pre-loaded. You do not install anything during birth — everything that can be baked ahead of time already is. Your job is to imprint identity, switch on what this cell needs, and wire its external surfaces.

On every eggState
Toolchain — bun, node, pi (latest), terminal toolkitInstalled, on PATH
The DNA at /root — identity files, .pi/, site/, scripts/, bin/Present, with __NAME__ / __MODEL__ / __PROVIDER__ / __THINKING__ / __MODEL_CHAIN__ placeholders intact
All in-tree extensions — memory, mentality, wiki, dreamOn disk under .pi/extensions/, none registered
All optional packages — pi-web-access, …Installed under .pi/npm/, none enabled

Eggs are kept fresh — re-baked periodically so the toolchain, pi, and packages stay current. Trust that the egg is recent; you never need to update or install anything on it.

The ritual

Run these in order. Use well_exec for commands that run on the egg, local bash for commands that run on the Mac. If a step's command fails with a network-class error (5xx, ECONNRESET, registry timeout), retry it once after 5s before reporting failure.

The blob's harness field picks the branch. A pi cell follows the full ritual — steps 1–9 below. A claude-code cell follows the claude-code branch, and a codex cell follows the codex branch — both shorter rituals that skip extensions, packages, and cells-side channels (a claude-code or codex cell is a coding machine, not the full capability stack — see docs/proposals/claude-code-harness.html and docs/proposals/codex-harness.html).

1 · Imprint identity

The cell learns its name. Substitute __NAME__ across the DNA, and the color chip into the tmux config.

# on the egg
sed -i 's/__NAME__/<name>/g' \
  /root/AGENTS.md /root/SOUL.md /root/IDENTITY.md \
  /root/CELLS.md /root/CONTACTS.md /root/HEARTBEAT.md /root/package.json

# on the Mac: compute the cell's color, then substitute on the egg
read CBG CFG < <(bash scripts/cell-color.sh <name>)
sed -i "s|__CELL_BG__|$CBG|g; s|__CELL_FG__|$CFG|g; s|__NAME__|<name>|g" /root/.tmux.conf

2 · Apply model config

The cell's brain is configured from the blob's model, provider, thinking, and chain.

# on the egg — model config lives in settings.json only; the identity
# files (SOUL.md, IDENTITY.md) are model-agnostic, leave them alone
sed -i 's/__MODEL__/<model>/g'        /root/.pi/settings.json
sed -i 's/__PROVIDER__/<provider>/g'  /root/.pi/settings.json
sed -i 's/__THINKING__/<thinking>/g'  /root/.pi/settings.json
# chain: the DNA placeholder is a quoted string ("__MODEL_CHAIN__") so the
# file stays valid JSON — sed swaps the quoted token for a bare JSON array.
# Use | as the delimiter (chain entries contain /).
sed -i 's|"__MODEL_CHAIN__"|<chain-json>|g' /root/.pi/settings.json

# validate — pi crash-loops on a malformed settings.json
jq . /root/.pi/settings.json > /dev/null

If the blob's provider is anthropic — a pi cell on an Anthropic model — the cell must reach api.anthropic.com directly with its ANTHROPIC_API_KEY, not through the subscriptions proxy (pi-via-Max is fingerprint-blocked; the paid key is clean). Drop the routing flag and re-run the pi patches so the Anthropic baseUrl is restored to direct:

# on the egg — ONLY when the blob's provider is "anthropic"
touch /root/.anthropic-direct
sudo bash /root/scripts/apply-pi-patches.sh

3 · Write the status file

The tmux bar reads this. Channels start empty — step 6 fills them.

# on the egg
mkdir -p /root/.pi
echo '{"harness":"<harness>","channels":[]}' > /root/.pi/status.json

4 · Switch on extensions

All four in-tree extensions are already on disk. Register only the ones in the blob's extensions — the rest stay on disk, switched off. Do not delete the unused ones. If extensions is empty, skip this step.

# on the egg, for each <ext> in the blob's extensions array
jq --arg p ".pi/extensions/<ext>/index.ts" \
  'if (.extensions | index($p)) then . else .extensions += [$p] end' \
  /root/.pi/settings.json > /tmp/s.json && mv /tmp/s.json /root/.pi/settings.json

5 · Register the site service

The cell's public face at <name>.cells.md is served by the cell itself, and the same server exposes the /agent bridge. Register the service, then flip the well URL public so external requests reach it.

# on the Mac
bash scripts/register-site-service.sh <name> <egg-well-name>
well url update --auth public -s <egg-well-name>

6 · Wire channels + the cloud edge

Deploy the per-cell Cloudflare Worker (always), then bind any requested channels.

# on the Mac — always
bash scripts/deploy-cell-worker.sh <name> <egg-well-name>

# then, for each entry in the blob's channels array:
bun scripts/bind-channel.ts <name> slack    # if channels includes "slack"
bun scripts/bind-channel.ts <name> email    # if channels includes "email"

bind-channel.ts creates the Slack channel (and invites the owner), writes the channel→cell binding, mirrors it to the Cloudflare KV the front-door workers read, and updates /root/.pi/status.json's channels array — all idempotent. If channels is empty, only the worker deploy runs.

7 · Checkpoint

Take a clean restore point of the fully-configured cell before declaring it born.

well_checkpoint  name: <egg-well-name>  comment: "born-<name>"

8 · The end-test

Birth is not done until the cell is proven working. Run every check — collect failures, don't stop at the first.

If any critical check fails, the birth failed. Degradations (a channel didn't bind, the worker is slow to come up) are noted in the outcome message but don't fail the birth.

9 · Report + record

Call report_outcome — success: true only if every critical end-test check passed.

  • Success: report_outcome(success: true, message: "cell <name> alive · <model> · <degradations, if any>")
  • Failure: report_outcome(success: false, message: "step <N>: <what broke>")

On success only: append one line to the activity log, then tell the user exactly one line — "Cell <name> is alive. Talk to it with cells talk <name>." No caveats, no warnings.

If something fails

Stop at the first failed step. Skip straight to step 9 (or c7), report_outcome with success: false and a one-line message naming the step and what broke. Don't try to recover the cell in place — the CLI sweeps the egg on a failed outcome, and a fresh egg is faster than a half-born one.
