Cell lifecycle latency

Birth, sleep, wake, talk — how long each step takes, in plain English and in numbers.

The short version

Bringing a cell to life from nothing takes about 6 seconds. Putting it to sleep is instant. Waking it up again takes about a second. Then chatting with it again is another second or so. The expensive part is the very first time you breathe life into a cell. Everything after that is fast.

Shortcut: skip the explicit wake

Easy version

You don't have to wake a cell before talking to it. If you just type cells talk <name> "hi" on a sleeping cell, it'll wake itself up automatically and respond. But that combined operation takes about 8 seconds instead of the ~2 seconds you'd get by waking first and then talking.

Two-step (explicit wake, then talk)

cells wake mycell  ~1s

cells talk mycell "hi"  ~1.2s

Total: ~2.2s

One-step (talk auto-wakes)

cells talk mycell "hi"  ~8.2s

Total: ~8.2s

The auto-wake path bundles a longer ssh-accept poll loop plus a cold agent spawn, which adds up.

When does each shape matter?

  • Auto-wake is best when you don't care about waiting — script a quick check, fire and forget.
  • Wake then talk is best when you want it to feel snappy — wake while you're typing your prompt, then talk is instant.

Technical details

Technical

Measurement methodology

Two pty-wrapper scripts run end-to-end timing:

  • /tmp/v13-first-token.py — 10 trials of bun run cells birth against a fresh 10/10 warm pool. Measures from execvp to the first byte after the cell-XXXXXX> prompt label.
  • /tmp/v15-cycle-latency.py — for each cell, runs cells talk → cells sleep → poll wells until status flips → cells wake → poll wells until status flips → cells talk again. Captures CLI wall-clock + wells-side status-flip times separately.

What can throw the numbers off

The numbers above are under steady-state conditions. Things that can change them:

  • Cold pool — if no warm eggs are ready, birth falls back to a fresh well create from ubuntu-base, adds ~60-90s for the per-egg provisioning step.
  • Burned ssh+pi sessions — if a cell's host-bridge session died but the VM stayed running, the next talk pays a cold ssh+pi spawn (~545ms extra).
  • Wells substrate bounces — if welld restarts mid-talk, you'll get a transient 5xx and a retry.
  • LLM provider hiccups — deepseek/anthropic upstreams can drift the first-byte by seconds.
